# 对象如何传递

求职C++实战总册 · 值、借用与资源接口 · C++17

同样是把对象交给函数，可能发生值复制、借用、独占资源转移，也可能让另一个对象共同拥有它。接口应当让这些差异看得出来。本章从参数与返回值出发，再实现一个具有独立内容的缓冲区，把复制、移动、异常提交与借用期限接在一起。

## 1. 先决定调用前后谁拥有对象

### 普通值对象：先让成员自己管理资源

名字和一组整数都需要独立保存时，string和vector已经提供拥有、复制与销毁。Record的默认复制会分别复制成员的值；修改副本不改变原记录。无需为了“类包含动态内存”再写一遍析构、深复制和移动代码。

```cpp
struct Record {
    std::string name;
    std::vector<int> values;
    int revision = 0;
}; // No manual lifetime code: members already own their resources.

inline Record copy_and_edit(const Record& source, std::string name) {
    Record result = source;
    result.name = std::move(name);
    return result;
}
```

这里的Rule of Zero不是“永远不准写特殊成员”，而是**资源管理已经由成员完成时，让成员的语义自然组合起来**。若成员是裸的拥有指针，默认复制只复制地址；若成员是unique_ptr，默认复制通常会被删除；若同时保存指针和长度，还要检查默认移动能否保持二者的不变量。后面的IntBuffer就需要显式处理这种关系。

### 借用、消费和重新绑定，是三种接口

| 调用的目的 | 常见参数形式 | 这次调用承担的责任 |
|---|---|---|
| 读取已有对象 | `const T&` | 借用；不延长对象寿命 |
| 修改已有对象 | `T&` | 借用并允许修改对象 |
| 允许没有对象 | `const T*`／`T*` | 借用；约定空指针的含义 |
| 取得独占所有权 | `unique_ptr<T>` | 按值接收拥有者，调用方显式转移 |
| 更换调用方的独占拥有者 | `unique_ptr<T>&` | 可重置／替换该拥有者 |
| 保存一个普通值 | `T` | 接收独立的值，随后可移动进成员 |
| 真正保留共同所有权 | `shared_ptr<T>` | 接收并保留／转交共同拥有关系 |

只读、修改和允许空值可以直接通过对象或裸指针表达，不要求调用方必须使用某一种智能指针。

```cpp
inline std::size_t value_count(const Record& record) noexcept {
    return record.values.size();
}
inline std::size_t optional_value_count(const Record* record) noexcept {
    return record ? record->values.size() : 0;
}
inline void append_value(Record& record, int value) {
    record.values.push_back(value);
}
```

`T&`本身不负责保活。调用期间对象必须仍存在；函数若保存这个引用，还需要更长的外部寿命约定。`const T&`限制的是通过这个引用进行的修改，也不表示对象在其他地方不会变化。

消费和更换拥有者直接写进接口。consume_record按值取得拥有者，本例要求非空；replace_record接收拥有者的引用，先创建新记录，成功后再替换旧记录。

```cpp
inline std::unique_ptr<Record> make_record(std::string name) {
    auto result = std::make_unique<Record>();
    result->name = std::move(name);
    return result;
}
inline std::string consume_record(std::unique_ptr<Record> record) {
    if (!record) throw std::invalid_argument("record required");
    return std::move(record->name);
}
inline void replace_record(std::unique_ptr<Record>& target, std::string name) {
    auto prepared = make_record(std::move(name));
    target = std::move(prepared);
}
```

`consume_record(std::move(owner))`之后，原unique_ptr为空；函数内的局部拥有者负责最终销毁。`replace_record(owner, name)`则可能改变owner指向谁。纯读取函数写成`const unique_ptr<T>&`会无故限制调用方的拥有方式；需要读取的通常只是T。

### 右值引用参数绑定，不等于已经转移

`T&&`可以绑定右值，但绑定一个引用不会另建T对象。函数内部的命名参数仍是左值表达式，真正构造下一个拥有者时再显式移动。

```cpp
inline std::unique_ptr<Record> bind_only(std::unique_ptr<Record>&& input) {
    // Binding input alone has not moved ownership. This construction does.
    auto owned = std::move(input);
    return owned;
}
```

不要将“函数接受了`unique_ptr<T>&&`”解释成“进入函数前指针已经为空”。上例是在构造owned的那一行转移。对于明确消费的普通接口，按值unique_ptr通常更直接。

## 2. 独占资源：观察、转交和释放

### get、reset与release分别做什么

get只取得借用指针；reset会释放旧资源并接管新资源；release交出指针并让拥有者变空，资源仍然存在，释放责任也随之交给调用者。

```cpp
inline int inspect_reset_release() {
    auto owner = std::make_unique<int>(7);
    int* observer = owner.get();  // Borrow only.
    const int saved = *observer;
    owner.reset(new int(9));      // Old observer is now invalid.
    int* released = owner.release(); // owner becomes empty; resource still alive.
    std::unique_ptr<int> adopted(released);
    return saved + *adopted;
}
```

reset之后不能继续使用指向旧对象的observer。release之后若无人接管，资源就会泄漏；跨C接口需要交接时，优先让下一位拥有者立即接住。`owner.reset(owner.get())`会先删除owner仍记着的同一个对象，不是“重新确认拥有”。

数组的释放方式也属于拥有合同：`unique_ptr<T[]>`对应数组删除，`unique_ptr<T>`对应单对象删除。需要大小、复制和插入时，vector通常直接满足需求。

### const拥有者，不等于const对象

`const unique_ptr<int>`不允许更换它持有的指针，却仍允许修改那个int；`unique_ptr<const int>`才限制被指对象。两层const可以同时存在。

```cpp
static_assert(std::is_same_v<
    decltype(*std::declval<const std::unique_ptr<int>&>()), int&>);
static_assert(std::is_same_v<
    decltype(*std::declval<const std::unique_ptr<const int>&>()), const int&>);

inline int const_owner_example() {
    const auto owner = std::make_unique<int>(3);
    *owner = 4;  // const owner, mutable owned object.
    return *owner;
}
```

自制指针可以选择传播const，那是另一个接口设计。不能由某个教学智能指针的`const T& operator*() const`，推导标准unique_ptr也这样工作。

### C资源也可以交给RAII

文件句柄的销毁操作是fclose，不能交给默认delete。自定义deleter把正确的释放动作接到unique_ptr上；提前返回或抛异常时，拥有者仍会完成清理。

```cpp
struct CloseFile {
    void operator()(std::FILE* file) const noexcept {
        if (file) std::fclose(file);
    }
};
using File = std::unique_ptr<std::FILE, CloseFile>;

inline File open_file(const char* path, const char* mode) {
    File file(std::fopen(path, mode));
    if (!file) throw std::runtime_error("open failed");
    return file;
}
inline void close_checked(File& file) {
    auto* raw = file.release();
    if (raw && std::fclose(raw) != 0)
        throw std::runtime_error("close failed");
}
```

析构路径用于清理，不向外抛异常。若调用方必须知道关闭是否失败，就走显式的close_checked；它先交出句柄，随后无论fclose报告什么，都不再把同一句柄关闭第二次。这里讨论的是资源释放，不承诺写入数据已经持久化到磁盘。

### 转成基类拥有者时，还要看销毁接口

`unique_ptr<Derived>`能转换成`unique_ptr<Base>`，不代表任意Base都适合通过基类指针删除派生对象。使用默认删除器时，下面的基类具有虚析构函数。

```cpp
struct BaseRecord {
    virtual ~BaseRecord() = default;
    virtual int value() const = 0;
};
struct CountRecord : BaseRecord {
    int value() const override { return 7; }
};
inline std::unique_ptr<BaseRecord> make_polymorphic_record() {
    return std::make_unique<CountRecord>();
}
```

如果基类缺少适当的虚析构，通过默认`delete Base*`销毁派生对象会产生未定义行为；智能指针没有自动修复这个类型合同。本章不展开继承布局与完整多态设计。

## 3. 一个有独立内容的缓冲区

### 深复制、移动与状态不变量放在一起实现

IntBuffer拥有一段整数数组，并记录长度。它的合同是：副本拥有独立数组；移动转交数组，源对象变为空；空对象长度为0；at在越界时抛异常。实际业务若不需要自定义这些规则，直接使用vector<int>即可。

```cpp
class IntBuffer {
    std::size_t size_ = 0;
    std::unique_ptr<int[]> data_;
public:
    explicit IntBuffer(std::size_t size = 0)
        : size_(size), data_(size ? std::make_unique<int[]>(size) : nullptr) {}
    ~IntBuffer() = default;
    IntBuffer(const IntBuffer& source) : IntBuffer(source.size_) {
        if (size_) std::copy_n(source.data_.get(), size_, data_.get());
    }
    IntBuffer& operator=(const IntBuffer& source) {
        IntBuffer prepared(source);
        swap(prepared);
        return *this;
    }
    IntBuffer(IntBuffer&& source) noexcept
        : size_(std::exchange(source.size_, 0)), data_(std::move(source.data_)) {}
    IntBuffer& operator=(IntBuffer&& source) noexcept {
        if (this != &source) {
            data_ = std::move(source.data_);
            size_ = std::exchange(source.size_, 0);
        }
        return *this;
    }
    void swap(IntBuffer& other) noexcept {
        std::swap(size_, other.size_);
        data_.swap(other.data_);
    }
    std::size_t size() const noexcept { return size_; }
    int& at(std::size_t index) {
        if (index >= size_) throw std::out_of_range("buffer index");
        return data_[index];
    }
    const int& at(std::size_t index) const {
        if (index >= size_) throw std::out_of_range("buffer index");
        return data_[index];
    }
};
```

这段实现的几个决定互相关联：

- **复制构造没有旧资源要清理。** 先分配目标数组，再复制元素；分配失败时新对象没有构造完成，源对象不受影响。
- **复制赋值已有旧状态。** 先完整构造prepared，成功后用不抛异常的swap一起提交指针和长度。准备失败，原目标保持原值；交换后prepared接走旧资源，离开作用域时释放。
- **移动不能只考虑指针。** 默认移动unique_ptr会让源指针变空，但size_t仍按值复制。自定义移动同时把源长度设为0，保持源对象的合同。
- **自复制与自移动分别处理。** 复制赋值通过准备副本自然支持自复制；移动赋值显式判断自身，保留原值。这是本类选择的明确合同，不从一次运行推广到所有类型。

指针和长度各自都能合法保存，并不证明它们组合后的状态正确。多槽位容器、迭代器缓存或其他拥有多个相关成员的类，同样要检查操作中途抛出后，不变量是否仍成立。

### std::move改变表达式，真正调用什么还看候选

std::move不负责搬运、释放或清空；它允许后续操作把表达式当作可移动的右值。是否真的调用移动构造，仍取决于类型、const和候选函数。

```cpp
struct CopyFallback {
    CopyFallback() = default;
    CopyFallback(const CopyFallback&) = default; // Suppresses implicit move.
};
struct MoveDeleted {
    MoveDeleted() = default;
    MoveDeleted(const MoveDeleted&) = default;
    MoveDeleted(MoveDeleted&&) = delete;
};
struct DefaultedMove {
    MoveDeleted member;
    DefaultedMove() = default;
    DefaultedMove(const DefaultedMove&) = default;
    DefaultedMove(DefaultedMove&&) = default; // Defined as deleted, then ignored.
};

inline IntBuffer copy_from_const(const IntBuffer& source) {
    return IntBuffer(std::move(source)); // const IntBuffer&& selects const& copy.
}
inline CopyFallback copy_from_rvalue(CopyFallback source) {
    return CopyFallback(std::move(source)); // No move candidate: copy is viable.
}
// MoveDeleted result(std::move(source)); is ill-formed: deleted move wins.
```

| 情况 | 关键结果 |
|---|---|
| 命名的右值引用变量 | 表达式仍为左值，需要时再move |
| `std::move(const T)` | 得到`const T&&`；通常不能绑定`T&&`移动构造，有`const T&`复制时可能复制 |
| 没有声明移动构造，但有可用复制构造 | 右值可以绑定复制构造的const引用 |
| 显式声明`T(T&&)=delete` | 该候选仍参加重载，若被选中，不能退回复制来绕过删除 |
| 默认化的移动构造因成员不可移动而被定义为删除 | 这类移动构造会被忽略，仍可能使用复制；DefaultedMove展示此区别 |
| unique_ptr的const源 | 通常既不能移动，也没有复制可用，相关构造会失败 |

标准库对象移动后，通常处于有效但值未指定的状态，除非具体类型另有保证。可以销毁、重新赋值，其他操作仍须满足其前置条件。不能统一假设所有容器都为空；本章IntBuffer则主动提供了移动后长度为0的更具体合同。

### noexcept会影响重新安置元素的选择

为了在搬移失败时保留旧值，有些实现会在移动可能抛出且复制可用时选择复制。`std::move_if_noexcept`直接表达了这种选择。

```cpp
template<class T>
T relocate_one(T& source) {
    return T(std::move_if_noexcept(source));
}
// Copies a copyable T whose move may throw; moves when copy is unavailable.
```

若T不可复制，即使移动可能抛出，仍可能只能移动。由此可见，“容器只有在noexcept时才move”过强；实际保证还取决于元素能力与具体操作。noexcept也是承诺，异常若越过该函数的边界，程序会终止，不能为了获得性能标签随意添加。

### 工厂返回值，不必手动把局部对象move出去

按值返回适合交出一个独立结果。C++17中，返回同类型纯右值直接构造结果对象；返回命名局部对象可进行NRVO，未进行时按相应规则选择移动或复制。

```cpp
inline IntBuffer zeros(std::size_t count) {
    return IntBuffer(count); // C++17: no intervening IntBuffer copy/move.
}
inline IntBuffer filled(std::size_t count, int value) {
    IntBuffer result(count);
    for (std::size_t i = 0; i < count; ++i) result.at(i) = value;
    return result; // NRVO is permitted; otherwise move selection applies.
}
```

`return std::move(result)`会让表达式不再是满足NRVO条件的那个名字，可能妨碍这条省略路径。正常写`return result`即可。返回局部对象的引用则是另一回事：函数退出后局部对象销毁，引用不会把它带出去。

## 4. 借用返回值：少复制，也要保留有效存储

### view带范围，不带拥有责任

prefix_view返回原字符中的一段，复制这个view不会复制字符，也不延长字符的寿命。需要让结果独立存在时，prefix_owned复制出自己的string。

```cpp
inline std::string_view prefix_view(std::string_view text, std::size_t count) {
    return text.substr(0, std::min(count, text.size()));
}
inline std::string prefix_owned(std::string_view text, std::size_t count) {
    return std::string(prefix_view(text, count));
}
inline void append_exact(std::string& output, std::string_view part) {
    if (!part.empty()) output.append(part.data(), part.size());
}
```

例如先保存`std::string input`，再取得它的prefix_view，在input仍有效且未使字符地址失效时使用该view即可。把临时string交给只在调用期间读取的函数通常没有问题；把对临时string的view存下来供下一条语句使用，则已经超出临时对象的寿命。

view还包含长度。它可以只指向一个string的前缀，也可以包含中间的NUL；data()不承诺在view末尾有结束符。append_exact显式传长度，不会误把底层后续字符也追加进去。

### 同一个getter：左值可以借用，临时对象返回拥有值

只返回`const string&`的getter，若从临时对象调用，得到的引用可能在完整表达式结束后失效。可以用成员函数的引用限定区分来源对象。

```cpp
class Message {
    std::string text_;
public:
    explicit Message(std::string text) : text_(std::move(text)) {}
    const std::string& text() const & noexcept { return text_; }
    std::string text() && { return std::move(text_); }
    std::string text() const && { return text_; }
};
// Lvalue access borrows; temporary access returns an owning value.
```

`message.text()`在message为左值时借用成员；`Message("abc").text()`按值返回，结果自己拥有字符。const临时对象不能移动出可修改的成员，本例为它提供复制返回值，仍保持结果独立。

接收方式也会改变结果：`auto value = message.text()`从借用结果复制出string；`const auto& value = message.text()`继续借用message内部的string。后者的有效期受message约束，不因value是const引用就自动延长message的寿命。

接口只能表达借用策略，调用方仍需保持持有者。把本例返回的临时string再转换成string_view并长期保存，仍会产生悬垂；不能因为getter本身返回了拥有值，就认为任何进一步借用都安全。

## 5. 确实需要共同拥有时

### shared_ptr参数应当使用它的拥有语义

需要把对象保存到调用之后时，按值接收shared_ptr，再移动进成员。只有部分调用会保留对象时，const引用可以省去不保留分支的那次拥有者复制；真正需要时再复制。

```cpp
class RecordKeeper {
    std::shared_ptr<Record> retained_;
public:
    void retain(std::shared_ptr<Record> record) {
        retained_ = std::move(record);
    }
    void retain_if(const std::shared_ptr<Record>& record, bool keep) {
        if (keep) retained_ = record;
    }
    void clear() noexcept { retained_.reset(); }
    std::size_t size() const noexcept {
        return retained_ ? retained_->values.size() : 0;
    }
};
```

shared_ptr复制通常共享同一个对象，并不深复制Record；修改该Record会被其他拥有者看到。它延长对象寿命，不自动保证对象的并发读写安全。只借用一次时，前面的Record引用接口仍更直接。

`const shared_ptr<T>&`本身不增加共同拥有，仍要检查调用期间原拥有者是否可能被别处重置。若调用链能经别名重置外部owner，应先取得不交给该链修改的局部拥有者，再借用其对象，例如`if (auto pin = owner) use(*pin);`。即使调用内部重置了原owner，pin仍把对象保留到本次调用结束；这与让shared_ptr存储成员地址的别名构造是两回事。

### weak_ptr观察，使用时先取得一份临时拥有

weak_ptr不延长对象寿命。lock尝试取得shared_ptr；成功后将这份局部拥有保持到本次使用结束。

```cpp
inline std::optional<std::string> observed_name(const std::weak_ptr<Record>& observer) {
    if (auto owned = observer.lock()) return owned->name;
    return std::nullopt;
}
```

本例用optional区分“仍存在的名字”和“对象已过期”，返回的string是独立副本。先expired()再另行使用一个裸指针，不能获得同样的保活效果。共同拥有关系若形成环，单纯增加shared_ptr无法释放这个环；不需要共同拥有的反向观察可使用weak_ptr。

### 指向谁，与共同拥有谁，不总是同一个问题

别名构造允许shared_ptr存储指向成员的地址，同时共同拥有外层对象。即使只剩revision这个shared_ptr，Record仍应存活。

```cpp
inline std::shared_ptr<int> share_revision(std::shared_ptr<Record> owner) {
    if (!owner) throw std::invalid_argument("record required");
    return std::shared_ptr<int>(owner, &owner->revision);
}
template<class A, class B>
bool same_owner(const std::shared_ptr<A>& a, const std::shared_ptr<B>& b) noexcept {
    return !a.owner_before(b) && !b.owner_before(a);
}
```

`get()`比较存储的地址；same_owner利用owner_before比较共同拥有关系。不要从现有shared_ptr的get()重新创建一个默认删除的shared_ptr：那会建立第二个不相干的控制块，而非加入原来的共同拥有。

本章的选择原则可以落回三个问题：结果是否需要独立存在，调用是否改变拥有关系，借用所依赖的对象能活到何时。先回答这些，再选择值、引用、view或智能指针。
