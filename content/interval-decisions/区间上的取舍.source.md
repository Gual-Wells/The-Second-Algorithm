# 区间上的取舍：覆盖、冲突与收益

<a id="chapter-entry"></a>
## 先决定保留什么，再决定怎样排序

两份日程都写着起点和终点，你却可能在回答完全不同的问题：合并忙碌时间，要保留的是覆盖位置；安排所有住客，要保留每个请求；只看尽可能多场电影，可以舍弃请求；项目各有收益，则“多选一个”未必更好。端点对只是表示，不能替你决定目标。

本章面向已经能读循环、理解数组和基本复杂度，但还不熟悉C++容器与算法接口的读者。我们从具体任务建立需要保存的信息，在同一条推理旁边读实现。第一次需要的C++知识就近讲解；后续点击对应术语查看，算法的新理由仍在当前位置讲清。

行进路线分成四步：先把覆盖位置整理成有序并集；再让所有请求同时存在，计算峰值并构造资源分配；然后限制资源，在数量、命中、连续覆盖和收益之间选择方法；最后把已经会用的候选堆用于离线点查询。读完后，应能说出为什么某个状态足够、哪个条件改变会使它不够，以及该换哪种状态。

本章处理预先取得的静态一维区间。任意在线取消、逐区间包含计数、不同资格的资源、多资源加权收益等问题会改变需要维护的信息，章末会标出边界。

<a id="endpoint-model"></a>
## 相接的两个端点，是否冲突

先比较 `[1,2]` 与 `[2,3]`：

| 任务如何解释端点 | 时刻2发生什么 | 同一资源能否连续接受 |
|---|---|---|
| 半开占用 `[start,end)` | 前者已结束，后者刚开始 | 可以，条件是前者 `end <=` 后者 `start` |
| 闭占用 `[start,end]` | 两者都占用时刻2 | 不可以，条件必须是前者 `end <` 后者 `start` |

[Movie Festival](https://cses.fi/problemset/task/1629/)允许结束后立即观看下一场；[Room Allocation](https://cses.fi/problemset/task/1164/)按整天入住，前一人离店日必须严格早于后一人入住日。[Projects](https://cses.fi/problemset/task/1140/)也按整天占用。不能把“区间通常写成方括号”当作题目的真实政策。[LC435](https://leetcode.com/problems/non-overlapping-intervals/)甚至明确约定只接触一个端点不算冲突。

还要区分两种长度。连续线段 `[3,3]` 的长度为0；它包含一个整数3，因此整数点数为1。闭区间允许这样的单点或单日请求；半开活动必须满足 `start < end`，本章不把空半开区间当作需要资源的活动。

下面的类型保存端点、负载和收益。返回的 `chosen` 是原输入的0基下标；`room_for` 按原输入顺序给出从1开始的房号。我们用一个明确的端点政策，使兼容关系贯穿分配、选择与加权计划。

## 只关心覆盖位置：一个还没有封口的并集

[LC56](https://leetcode.com/problems/merge-intervals/)要求把所有有重叠的闭区间合并。`[1,4]` 和 `[4,5]` 共享点4，应得到 `[1,5]`；`[1,4]` 和 `[5,6]` 之间却有连续实数空隙，不能因为端点是整数就合成一段。

最直接的做法是逐点标记，但端点很大时，坐标跨度和区间数量完全不是一回事。我们真正需要处理的是端点改变覆盖的地方。

<a id="merge-frontier-proof"></a>
## 为什么只需看最后一段

按起点升序排列。扫描时，结果中除了最后一段以外，其余段都已封口：它们与后面的输入之间已经出现空隙。以后输入的起点只会更靠右，不可能再回来填上那个空隙。最后一段保存当前连通覆盖的起点和最远右端。

读入下一段 `[s,e]` 时只有两种情况：

- `s` 大于最后一段的右端：空隙出现，原来最后一段可以封口，把当前段作为新的未封口部分。
- `s` 不大于最后一段的右端：两段相接或重叠，左边界已经最小，只需把右端更新为两者的较大值。

这不是“与前一个原始区间重叠就合并”。输入 `[1,10]、[2,3]、[9,12]` 中，第三段与第二段不重叠，却与尚未封口的并集 `[1,10]` 重叠。状态必须保存累计右端，不能只保存上一次读到的右端。

每段只处理一次；代价主要是排序，为 `O(n log n)`，扫描为 `O(n)`。结果最多有n段。函数按值接收输入，因此排序的是自己的副本，调用者原来的次序保留。

{{merge_closed}}

这里的标准设施是 `std::sort`、`std::vector` 和取较大边界的 `std::max`；合并的状态与判断仍由我们写。`std::set_union` 合并的是已经排序的元素序列，不能把“两个端点值属于集合”解释成“两个时间区间的几何并集”。

<a id="insert-reuse"></a>
## 输入已经整理好，就利用已有结构

[LC57](https://leetcode.com/problems/insert-interval/)的既有区间已经按起点排序，彼此没有公共点。加入一段 `[s,e]` 后，不需要把所有区间重新排序。

先复制右端严格小于s的那些段；它们完全在新段左边。然后连续读取与正在扩展的新段相接的区间，更新两端，直到下一段起点大于当前右端。把扩展后的新段加入结果，最后复制右侧其余区间。三段处理顺序对应三个连续的输入区域，总共只扫一遍，为 `O(n)`。

{{insert_closed}}

已有的互斥性是这个算法能只合成一个中间区间的理由。如果既有输入内部本来还有重叠，直接套这个入口不一定得到规范并集，应先用上一节的完整整理。

得到规范并集后，可以继续利用它，而不必重新对原区间做两两检查：

- 连续覆盖长度：累加每段 `end-start`。若任务问整数点数，闭区间改为 `end-start+1`；这是不同的度量。
- 点是否被覆盖：在并集里找最后一个起点不大于查询点的段，再检查查询点是否不大于该段右端。找不到这样的段即未覆盖。前驱的安全取得会在 [[Q000037|lower_bound与upper_bound]]、[[Q000038|multiset的重复状态]] 讲清。
- 哪些位置空闲：相邻并集段之间的空隙就是候选空闲段；给定查询窗口时还要裁剪窗口两端。连续闭区间 `[a,b]` 与 `[c,d]` 之间的空隙是开区间 `(b,c)`，不能把b和c也报为空闲。
- 一段目标是否全部被覆盖：若起点落在某个规范并集段内，只需再检查该段右端能否达到目标终点。目标若跨过两个不同并集段，必然经过中间空隙。

这些查询复用了并集已经完成的工作。它们不能回答“原来有几个人同时占用”，因为合并已经丢掉了重数。

<a id="containment"></a>
## 保留身份时，怎样判断包含关系

[Nested Ranges Check](https://cses.fi/problemset/task/2168/)问的是每条原区间是否包含别的区间、是否被别的区间包含。答案必须回到原输入位置，不能先合并。

将区间按起点升序、同起点按右端降序排列。当前段之前的所有段，起点都不晚于当前起点；因此当前是否被包含，只差“之前是否存在一个足够大的右端”。一个前缀最大右端就足够回答。相同起点时让长段排在前面，正是为了让它能包含后面的短段。

反过来，从右往左扫描。当前之后的所有段起点都不早于当前起点；若后缀中最小右端不大于当前右端，就存在被当前段包含的区间。两遍扫描都不需要保存所有历史端点：存在性问题由一个极值概括即可。

{{orders}}

这些小工具给区间补上原id、表达端点兼容，并建立按起点或终点的顺序。它们没有替我们决定应保存并集、极值还是候选集合。

{{containment_flags}}

排序为 `O(n log n)`，两遍扫描为 `O(n)`，索引与输出需要 `O(n)` 空间。这里按原题保证，没有两条完全相同的区间。若允许完全重复，副本互相包含，按单条顺序扫描会让组内首尾得到不对称答案；应把相同端点分组处理，不能直接声称当前接口已支持。

“有几个”又是新的问题。一个最大右端只能告诉你至少有一个，不知道有三个还是三十个。[Nested Ranges Count](https://cses.fi/problemset/task/2169/)需要保留端点分布，可以进一步研究压缩坐标后的频数与秩查询；本章实现的是包含存在性。

<a id="occupancy-cluster"></a>
## 所有请求都保留：只在端点更新占用

[Restaurant Customers](https://cses.fi/problemset/task/1619/)要求最大同时在场人数。每次进入令计数加1，每次离开减1；两个相邻事件之间没有任何变化，因此不需要访问中间的每个时刻。

将所有事件按坐标排序，扫描累计量并记录最大值。它保留的是重数，故 `[1,5]` 与 `[2,4]` 不能预先合成一条 `[1,5]`。合并仍知道哪里有人，却不知道中间曾有两个人。

<a id="peak-endpoint-proof"></a>
## 同一坐标的事件，先加还是先减

对闭占用，时刻x结束的请求与时刻x开始的请求同时在场：先加入开始量、记录峰值，再移除结束量。单点 `[x,x]` 也必须贡献一次占用。对半开占用，结束者已经释放：先减后加。若把闭区间同坐标的增减合成一个净变化再记录最大值，就可能把仅在这个点发生的峰值消掉。

从单位人数换成带宽或乘客数，只需把增减量换成正负负载w，活动量仍是之前事件的累计和。[Car Pooling](https://leetcode.com/problems/car-pooling/)规定同地点先下客后上客，应采用半开政策；计算峰值后，比较是否超过容量即可。带权负载必须全部接纳，和后面“选择哪些带收益项目”是不同目标。

{{peak_load}}

总共2n个事件，时间 `O(n log n)`、额外空间 `O(n)`。负载与累计类型见 [[Q000032|运算类型与数值范围]]。原Restaurant Customers保证所有到离时间互不相同，所以其样例不能替我们检验重复端点政策；重复端点由上面的占用模型决定。

如果只需单位峰值，还可以分别排序全部起点和终点，用两个指针按相同事件顺序扫描；它保存同一个计数不变量。若坐标范围很小，可以在每个坐标累计差分再做前缀和，代价变成 `O(n+U)`，U是坐标域大小。闭离散日程常在 `end+1` 撤销负载，但必须确认这个坐标存在且加1不会溢出；不能将这一技巧无条件用于连续时间。坐标可达十亿时，按域长分配数组通常比按事件排序更浪费。

<a id="room-allocation"></a>
## 从峰值数值，走到一份实际房间安排

[Room Allocation](https://cses.fi/problemset/task/1164/)不仅问最少房数，还要求按原输入顺序输出每个住客的房号。只算出峰值，尚未完成分配。

先按入住时间排序。每个已使用房间只需记录最后一位住客的离店时间：更早的住客都排在他之前，不影响下一次是否可接。每次查看释放最早的房间。若它与当前请求兼容，就重用这个房号、更新释放时间；若连它都不兼容，其他房间只会释放得更晚，只能开新房。

<a id="room-optimality"></a>
## 为什么新开的每一个房间都不可避免

设当前将第r个房间第一次打开。前r−1个房间的最后请求都未释放，因为连最早释放者也不兼容；这些请求又都已经开始，因为我们按起点处理。所以在当前起点上，至少r个请求同时占用，任何安排都需要r个房间。

算法确实只在这个情形开新房，因此它用的房数既不小于峰值下界，也没有超过任何可行安排必须支付的数量。它同时给出合法构造：同房连续请求都通过了端点兼容判断。这里“取最早释放”用于判断是否存在可重用房间；后面固定资源选择的目标会要求另一种取法。

需要动态取最小释放时刻，反复全排序每个房间会浪费工作。二叉小堆让最小值始终在根；入堆与出堆只修复一条祖先或后代路径。

<a id="manual-heap"></a>
## 手写堆：真正修复父子关系

把堆放在vector里，下标i的父亲为 `(i-1)/2`，左右孩子为 `2*i+1` 和 `2*i+2`。小堆的不变量是每个父亲都不大于孩子，并不要求整段数组已经排序。这个局部关系足以推出根是全局最小：沿任何点到根的路径，值只会不增。

插入先追加在最后，只有新点到根的路径可能破坏关系。只要它小于父亲就交换并上移，其余父子关系不变。删除根时，先用末尾元素填根并移除末尾；现在只可能在根向下破坏。每次与两个孩子中较小者比较，必要时交换，再继续向下。先选较小孩子，才能保证交换后留在上面的值也不大于另一个孩子。

{{release_min_heap}}

树高为 `O(log(r+1))`，因此上浮或下沉的堆序修复最坏只走这么多层，取根为 `O(1)`。但这份push还先调用vector的push_back：某次扩容会搬移已有的r项，使那一次完整push花到 `O(r)`；把一串追加共同计算，push_back为摊销常数，故完整push为摊销 `O(log(r+1))`。pop不扩容，为最坏 `O(log(r+1))`。全部n次房间更新的总代价仍为 `O(n log(n+1))`，不能把它误写成每次vector追加都有最坏常数保证。空堆不能取根或删除根；调用者先检查。索引运算和循环边界的合法性来自当前元素数，不来自vector容量，参见 [[Q000028|vector的大小与容量]]。

{{allocate_manual}}

排序加n次堆操作使总时间为 `O(n log n)`，堆最多r≤n个房间。输出保存原id，因此排序并不改变最终房号数组的输入顺序。下面两版使用同一个分配算法，只替换堆操作的实现层。

<a id="selection-cluster"></a>
## 只保留一部分：最早结束的请求先选

现在资源只有一个，任务也可以不接。[Movie Festival](https://cses.fi/problemset/task/1629/)要求看尽可能多场完整电影，时间长短不带额外收益。

“最早开始”可能先拿一场跨越整天的电影，挡住几场短片；“最短时长”可能选一段跨在两场可连续观看的电影之间，也挡住两场。局部看起来节省时间，不等于给后续留下的可行集合更好。

按结束时刻升序考虑：若当前电影与已选最后一场兼容就选，否则跳过。第一次选最早结束者，后面不断重复这个决定。

<a id="activity-exchange"></a>
## 交换证明真正需要保住什么

取任意一个最多场次的最优计划，设它的第一场为o，贪心的第一场为g。因为g全局结束最早，`end(g) <= end(o)`。把最优计划第一场换成g，其余场次仍可接在g后面：它们原来接在o后面，而g没有更晚结束。数量没少、可行性没坏，所以至少存在一个最优计划以g开头。

固定g后，剩下的候选正是能接在g后面的电影，问题形式没有改变。对余下部分重复同样交换，最终得到贪心计划同样达到最优数量。证明保住的是“数量相同且结束不更晚”，没有说g的时长最短或收益最高。

{{choose_activities}}

时间 `O(n log n)`，选择数组最多n项。初始 `last_end=0` 不是断言第一个请求从0以后开始；它只在chosen非空后才读取，首个请求由短路条件直接接受。返回的是实际计划；最少删除数直接是 `n-chosen.size()`，不必重造一种“删除算法”。如果原题已经按结束时间排序，如[Codility MaxNonoverlappingSegments](https://app.codility.com/programmers/lessons/16-greedy_algorithms/max_nonoverlapping_segments/)，扫描本身只需 `O(n)`。

接触政策仍必须一致。电影或LC435按 `end<=next.start` 接续；闭区间互斥选择用严格 `<`。下面的点命中问题使用闭区间，不能把两种数量直接混算。

<a id="stabbing"></a>
## 用点命中每一段，为什么也看右端

[LC452](https://leetcode.com/problems/minimum-number-of-arrows-to-burst-balloons/)让一支竖直箭命中所有包含其横坐标的气球区间。要选的是点，要覆盖的是每条闭区间；这既不是合并，也不是保留最多任务。

取最早结束的尚未命中区间 `[s,e]`，在e放一个点。为什么可以把这一点永久定下来？任何完整方案都必须在 `[s,e]` 内放某点p。考虑所有尚未处理区间：它们的右端都不小于e。若某条原来包含p，那么其左端不大于p≤e，右端又不小于e，因此它仍包含e。把p移到e，不会丢失它原来负责的剩余区间，还可能命中更多。

删去被e命中的区间，继续处理。排序后只要当前左端大于最后选点，才需要新点；若等于，闭端点仍算命中。

{{stabbing_points}}

总时间 `O(n log n)`，输出即命中见证。每次迫使我们新选一点的那条区间，与此前这些“迫使新点”的区间两两无公共点；一个点不可能同时命中其中两条，所以它们的数量给出下界。算法恰好使用同样多的点，因而达到最少。

这也说明：采用相同闭区间相交政策时，最大两两不相交区间数等于最少命中点数。但 `[1,2]` 与 `[2,3]` 在电影式接续里可以选两场，在闭区间命中里一点2就够；政策不同，不能把两个答案强行认作相同。

<a id="continuous-cover"></a>
## 用片段覆盖整段目标，要改成最远推进

[Video Stitching](https://leetcode.com/problems/video-stitching/)允许把片段剪开，要求覆盖 `[0,T]` 的全部时间。这里选的是区间，必须覆盖的是整个连续目标。假设已有连续覆盖 `[0,covered]`，所有起点不大于covered的片段都可以与它接上；下一次应从这些候选中选右端最大的片段。

例如目标 `[0,5]`，片段 `[0,1]、[0,4]、[1,2]、[2,3]、[3,5]`。按最早结束选会先耗费 `[0,1]`，接着仍要继续补；直接选 `[0,4]` 再接 `[3,5]` 只用两段。“早点结束给后面让路”在这里没有价值，因为重叠不构成冲突，我们要的是更远的覆盖。

<a id="cover-dominance"></a>
## 一轮内全部看完候选，才提交选择

设本轮能接上的最远右端为f。任何完成目标的方案，其下一段也必须从当前连续覆盖接出去，不然covered右侧会留下空隙。若它下一段只到r≤f，用我们选的片段替换，不会缩短本轮能覆盖到的位置。原方案后续每段若有助于继续向右，都仍可从更远前沿接上；已经被f覆盖的片段可以直接省掉。因此存在一个不比最优方案更差的方案，先走到f。

按起点排序后，用指针读完 `start<=covered` 的全部候选，并取其中最大end。不能读到第一条可接片段就立即提交，因为同一轮后面可能有更远的。提交后，所有本轮候选都已被f支配，不必回头。若f没有严格大于covered，就没有任何片段能跨过当前边界，目标无解。单点片段不能推进连续覆盖。

{{minimum_cover}}

函数返回最少片段的一组原id；失败时 `possible=false` 且不返回一份看似完整的局部方案。排序 `O(n log n)`，扫描 `O(n)`。它只承诺 `T>0`；若目标本身长度为0，应先按具体任务决定是否需要一个命中点或根本不需片段，不能沿用正长度问题的无解分支。

[LC1326](https://leetcode.com/problems/minimum-number-of-taps-to-open-to-water-a-garden/)可把第i个水龙头转成 `[i-ranges[i],i+ranges[i]]`，再用同一机制覆盖 `[0,n]`。其端点为有界整数时，可先对每个左端保存最远右端，再按坐标推进，得到线性于坐标域的实现；这只是同一个最远推进的另一种候选整理方式。一般坐标仍适合排序。草带喷头等几何任务还需要先证明圆的哪一段真正覆盖整条带宽，不能只把圆的左右极点当作有效区间。

<a id="fixed-resources"></a>
## 固定k个资源，为什么不能继续只取最早释放

[Movie Festival II](https://cses.fi/problemset/task/1632/)有k个人，要最大化总观看场数。与最少房间问题相比，所有电影不必被接受，人数却不能无限增加。

仍按电影结束时间处理。每个已使用的人只记录其最后一场的结束时刻。当前电影开始于s：在所有能接它的人中，找**释放最晚**的人，把他的释放时刻替换为当前结束。这样保留更早空闲的人，给后面可能开始更早、却结束更晚的电影。

以k=2和电影 `(1,2)、(1,5)、(6,7)、(3,8)` 为例。先接前两场后，两人分别在2和5空闲。接 `(6,7)` 时，两人都可用；若消费释放2的人，剩下的释放5者无法接 `(3,8)`。若先消费释放5者，释放2者仍能接 `(3,8)`，四场全部保留。结束顺序不代表开始顺序，不能把“后处理的电影”误认为“一定更晚开始”。

若没有兼容的人，但已使用人数还小于k，可以启用一个新的人；否则跳过当前电影。只存已经使用者，便不需要虚构负无穷结束时刻来代表尚未使用的人。

<a id="fixed-resource-exchange"></a>
## 把整个后续安排换过去，才完成多资源证明

我们逐场维护这样一个事实：存在某个全局最多场次的计划，它在已经处理的电影上，与贪心的接受、拒绝和人员分配一致。开始时前缀为空，显然可以找到一个最优计划。

设当前电影为j，开始s、结束e。所有尚未处理电影的结束都不早于e，而半开电影有s<e。因此在任何一个人的后续安排里，j之前都不可能再塞进一场尚未处理的电影：那场若先结束才能接j，其结束应不晚于s<e，与处理顺序矛盾。若使用闭占用政策，即使允许s=e的单日任务，前驱也必须结束严格早于s，仍然严格早于e，同一论证继续成立。

**有兼容旧人员时。** 贪心选其中释放最晚者r，记释放时刻为 `t_r`。考虑与当前前缀一致的一个最优后续计划：

- 若它没有选j，看r上第一场未来电影x。如果r后面为空，直接加入j就能增加总场数，与最优矛盾；因此必有x。将x替换为j：j能接在 `t_r` 后面，且e不晚于x的结束，所以x后面的整条安排仍能接上。总场数不变。
- 若它已将j分给r，就不用改。
- 若它把j分给另一个旧人员q，j必是q的第一场未来电影。q也兼容j，而r选的是最晚兼容者，所以 `t_q<=t_r`。将q从j开始的整条未来安排，与r的整条未来安排互换。j可以接在r后面；r原来的第一场若存在，本来就与 `t_r` 兼容：半开时起点 `>=t_r`，闭占用时起点 `>t_r`。因为 `t_q<=t_r`，同一兼容关系在q上仍然成立。两条链内部次序都没有改，所有电影和场数都保留。
- 若最优计划把j分给一个尚未使用的人，也可交换两人的未来安排：尚未使用者没有前缀限制，能接r原来的尾链，j则能接r。

**没有兼容旧人员，但还能启用新人员时。** 把新人员记为r，视为没有前缀约束。若最优计划没选j，用同样的“替换r的首场未来电影”操作；若已选j，它不可能接在任何不兼容的旧人员之后，因此只能分给一个尚未使用者，将人员名字交换即可。

**没有兼容人员且k人已全部使用时。** 在任何与前缀一致的计划中，j都不能成为某人的第一场未来电影；前面又证明不能先加别的未来电影再接j，所以只能拒绝它。

三种情形都能把贪心当前决策纳入某个同样好的全局最优计划，归纳便贯穿全部电影。这个证明用到了同质资源、半开活动的正时长或闭活动的严格接续、完整接受和数量目标。收益不同、人员有资格限制、在线到达后不能重排，都不能直接引用它。

## 数量换成收益：为什么必须保存多个最优前缀

现在每个项目有收益。两段连续短项目各收益1，一段同时覆盖它们的长项目收益3，最早结束的数量贪心只得到2。若改成先选最高收益，也会被“一段收益3长项目，对上两段各收益2的短项目”击败。固定一个局部排名，无法判断今天放弃一点收益能换来多少后续机会。

[Projects](https://cses.fi/problemset/task/1140/)问最大总收益，按闭日程只可在结束日严格早于下一开始日时相接；[LC1235](https://leetcode.com/problems/maximum-profit-in-job-scheduling/)允许结束即开始。我们在同一个前缀模型里保留这项差异。

按结束时刻排序，给前i个项目定义 `dp[i]`：只使用这i个项目，能取得的最大收益。`dp[0]=0`，表示没有项目可选。设当前是排序后的第i个项目，收益w，开始s；在之前i−1个项目中，与它兼容者恰好构成一个前缀，长度记为p。

<a id="weighted-recurrence"></a>
## 为什么只剩取与不取两类，而不是遗漏其他安排

任何最优计划都要么不选当前项目，要么选它。

不选时，全部选择来自前i−1个，最好值就是 `dp[i-1]`。选它时，所有先前项目的结束都必须与s兼容；结束已排序，因此合法候选恰好是前p个。它们之间的最佳选择为 `dp[p]`，加上当前收益得到 `w+dp[p]`。反过来，前p个的最优计划确实能与当前项目拼接，所以这个值不仅是上界，也真实可达到。

于是 `dp[i]=max(dp[i-1],w+dp[p])`。从小到大计算，所需前缀都已算好；不再枚举指数多的完整子集。难点是证明“剩下的合法集合恰好是一个前缀”，而非仅把取/不取写成一个max。

看一组闭日程：A为 `[1,2]` 收益4，B为 `[2,4]` 收益7，C为 `[3,5]` 收益5，D为 `[6,7]` 收益3。它们已经按结束日排序：

| 当前项目 | 兼容前缀长度p | 不取当前项目 | 取当前项目 | 最佳前缀收益 |
|---|---:|---:|---:|---:|
| A | 0 | 0 | 4+0 | 4 |
| B | 0 | 4 | 7+0 | 7 |
| C | 1 | 7 | 5+4 | 9 |
| D | 3 | 9 | 3+9 | 12 |

B不能接A，因为两者都占用第2天；C能接A，D再接上A和C，得到12。若同样四对数字改为允许结束即开始，B的兼容前缀变为1，A接B就有11，再接D得到14。只改接触政策，前驱与最优方案都可能改变，外层递推却不用改。

<a id="predecessor-search"></a>
## 前驱长度，既可以手写边界，也可以用标准算法

若每次从当前项目往左找兼容者，单次最坏 `O(n)`，总共 `O(n²)`。结束数组有序，可以用边界搜索把单次压成 `O(log n)`。

不能因为结束时刻递增，就用一个只前进的指针依次生成全部p。闭区间 `(1,3)、(5,6)、(2,7)` 已按结束排序，它们的兼容前缀长度却为 `0、1、0`：第三项开始得更早，前驱又退回去了。有序的是被查询的结束数组，不是查询阈值start；每项单独做边界查询没有这个错误假设。

这里直接返回兼容前缀长度p，范围为 `[0,count]`，不使用“找不到返回−1”的索引。维护半开未决范围 `[lo,hi)`：lo之前都兼容，hi及以后都不兼容；mid兼容时把lo推到mid+1，否则把hi缩到mid。每次严格缩短，结束时lo=hi正好是第一个不兼容位置，也是兼容项数。

<a id="budgeted-value"></a>
## 再限制总项数：k个名额不是k个资源

[LC1751](https://leetcode.com/problems/maximum-number-of-events-that-can-be-attended-ii/)要求一个人完整参加活动，最多选k项，最大化总收益；结束日仍然占用。这与Movie Festival II的k个同时可用资源完全不同：名额限制的是整个方案的总项数，不会在活动结束时恢复。三个互不相交活动用一个人就都能参加，但预算k=2时最多只能挑两个。

上面的前驱关系继续适用，新增的只有预算状态。定义 `value[c][i]`：在前i个项目中，最多取c项的最大收益。无项目或预算为0时答案都为0。对当前项目，仍按是否选它分类：

- 不选：`value[c][i-1]`，预算不变。
- 选：获得当前w，余下只能从兼容前缀p里最多取c−1项，得到 `w+value[c-1][p]`。

取两者较大就是完整转移。这里是“最多”，不必选满k；一项高收益活动可能比好几项互相冲突的活动更好，0预算也不代表无解。

先预计算所有项目的前驱p，再让c从1递增，每层让i从1递增。当前层需要它左侧的值，以及上一预算层的任意前缀值。两条vector已经够用：`previous[p]` 保存上一预算层，`current[i-1]` 保存本层左侧；一层算完，交换两条vector的内容，继续下一层。每一层都从0列开始并覆盖其他各列，所以不必把旧数组逐格清零。

{{bounded_weighted}}

为什么不能让选当前项目时也读取本预算层的p？因为那样没有支付这一个名额。两条兼容单日活动收益4和5，预算1应得到5；若用 `w+current[p]`，就会错误得到9。也不能只保留前缀i的相邻两行：p可以跳到很远的前缀，上一预算层的那些值仍然需要。预算外层的滚动安排，正好保留了这些依赖；完整二维表也能按合法依赖顺序计算，只是占更多空间。

时间为 `O(n log n+nk)`，滚动表与前驱等辅助存储为 `O(n)`。LC1751给出 `1<=k<=n` 且 `nk<=10^6`，所以n本身可到 `10^6`，不能错误假定它也只到200000。另一方面 `k²<=nk<=10^6` 推出k≤1000，单项收益≤ `10^6`，最多取k项使答案≤ `10^9`，原题int返回值在 [[Q000032|运算类型与数值范围]] 的目标环境内可表示；核心依然用long long计算。这个滚动接口只返回收益，没有保留前面完整DP用于恢复方案的全部决定，因此不承诺返回一组下标。

<a id="offline-query-cluster"></a>
## 反复问一个点：保留最短的仍有效候选

[LC1851](https://leetcode.com/problems/minimum-interval-to-include-each-query/)给很多查询点q，每次求包含q的原区间中，整数点数 `end-start+1` 最少者；没有则返回−1。注意要找原区间，不是并集中的最短段。合并会丢掉 `[4,4]` 这样的好答案。

每次把所有区间扫一遍，需要 `O(nm)`。所有查询预先给出时，可以先按点值升序处理，并带上查询原id。区间也按起点排序；查询点走到q，就把所有 `start<=q` 的区间加入候选。这样不必每次重新检查左端。

候选按 `(整数长度,右端)` 放入小堆。加入只保证左端已到达，右端还可能已过期。回答前不断删除 `end<q` 的堆顶，直到堆空或堆顶仍覆盖q。

<a id="offline-expiration-proof"></a>
## 为什么只清理堆顶，不清理整个堆

堆里可能埋着已经过期的长区间，但它排在当前堆顶后面，不可能提供更短答案。只要堆顶有效，它就是所有已加入区间中长度最小的有效候选；任何更短元素都应排到它前面，已被检查并删除或就是它自身。

一个区间右端小于当前q后，对所有后续不减的查询点也都会过期，所以删除是永久安全的。若不先排序查询，删除给较大点无效的区间后，再处理较小点就可能丢掉正确答案；“离线重排”正是这次状态简化成立的条件。

{{minimum_query_lengths}}

每个区间最多入堆一次、出堆一次，查询排序为 `O(m log m)`，总时间 `O(n log n+m log m+(n+m)log n)`，额外空间 `O(n+m)`。同一个查询值重复出现可以各自恢复到原位置，算法不要求查询互异。堆设施复用 [[Q000035|priority_queue的接口]]；这里的新依据是候选进入、永久过期与目标最小值，并不是房间分配的最优性证明。

| 峰值占用、负载是否超容量 | 全部请求保留；端点政策明确 | 事件增减与活动量 | `O(n log n)`；小坐标域才考虑按域差分 |
| 最少资源以及每条的分配 | 同质可复用资源，所有请求必接 | 起点扫描，最早释放小堆，深度下界 | `O(n log n)`；手写堆/适配器/堆算法是同方法的实现层 |
| 一个资源最多接几条、最少删几条 | 完整请求，等权数量 | 最早结束的兼容选择及原id | `O(n log n)`；收益不同不能照搬 |
| 最少点命中每条区间 | 闭区间，点可以共用 | 最早结束的未命中段，选其右端 | `O(n log n)`；相同相交政策下才与最大互斥数联系 |
| 最少片段覆盖整段连续目标 | 可重叠、可剪切，每片代价相同 | 当前可接候选的最远右端，严格推进 | `O(n log n)`；没有推进即无解，不用最早结束 |
| 固定k资源最大总数量 | 同质资源，半开正时长或闭占用严格接续，离线 | 结束排序，最大兼容释放前驱 | `O(n log(n+1)+n log(k+1))`；不是只取小堆顶，也未解决带权多资源 |
| 一个资源最大总收益及计划 | 结束排序后兼容集合成前缀 | 前驱边界、选择/跳过dp、回溯 | `O(n log n)`、`O(n)`空间；增加总项数限制时见下一行 |
| 一个资源最多k项的最大收益 | k是全局项数预算，接触政策明确 | 复用前驱，预算×前缀dp，按预算层滚动 | `O(n log n+nk)`、`O(n)`空间；接口只返回值，不是k资源算法 |
| 每个点的最短原区间 | 查询可离线重排 | 起点纳入、长度小堆、右端永久过期 | 排序与堆更新；不适用于任意顺序在线撤销后仍要回查 |

这些方法共享排序、边界与容器，却各自保存不同的信息。开始做一道新题时，先写清结果对象、必须保留的身份、接触政策和允许舍弃什么，再从表中选择机制。

还有两条容易因端点外形相同而误套的边界。[LC1353](https://leetcode.com/problems/maximum-number-of-events-that-can-be-attended/)只需在活动允许的日期中任选一天参加，不是完整占用整个区间。三项都可在 `[1,3]` 内任选一天的活动，逐日安排能参加三项；若当作三个完整闭区间，单资源只能选一项，模型已经变了。本文的完整区间选择不直接解决它。

连续覆盖也只在每个片段代价相同、目标最少片段数时比较最远推进。若 `[0,10]` 费用100，而 `[0,5]`、`[5,10]` 各费用1，伸得最远并不代表费用最小。需要保留费用与可达位置之间的取舍，不能把上文的最少片段贪心改一个累计变量就当作最低费用覆盖。
