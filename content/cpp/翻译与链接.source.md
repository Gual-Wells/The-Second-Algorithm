# 翻译与链接

同一个源文件能运行，拆成几个文件后出错，通常需要区分：**哪个阶段缺了什么，以及同一个名字是否仍表示同一个实体。** 头文件的include guard只解决一个翻译单元内的重复包含，不自动解决整个程序的定义关系。

| 现象 | 先检查 |
|---|---|
| 找不到头文件、宏展开不对 | 预处理输入和include路径 |
| 类型不完整、重载不匹配 | 当前翻译单元可见的声明与定义 |
| undefined reference／unresolved external | 是否链接了对应定义，名字和语言链接是否一致 |
| multiple definition／duplicate symbol | 是否把外部普通定义放进了多个翻译单元 |
| 编译链接都通过但仍违反ODR | 定义的token、查找结果、inline与模板条件是否一致 |

以下片段按文件名分组。参考源码保留各片段的唯一版本，验证时分别装配翻译单元；它们不是让所有头和源文件内容拼进一个.cpp。

下面的头在单一翻译单元里重复包含没有问题，但a和b都包含它之后，各自都有外部shared_count与increment定义，整个程序就出现重复定义。

## 2 共享定义与TU私有状态

### 2.1 头里声明，源里唯一定义

头文件提供足够编译调用的声明，state.cpp提供程序中的定义；链接时必须加入它。

{{odr-declaration-header}}

{{odr-one-definition}}

先调用first再调用second，得到1、2。`extern int shared_count;`只有声明；带初始化的`extern int shared_count = 0;`却是定义，不能因此把它随意放进共享头文件。

### 2.2 header-only：inline不是强制内联优化

C++17的inline变量和满足条件的inline函数允许相同定义出现在多个翻译单元，仍表示程序中的同一实体。这里first和second也得到1、2。

{{odr-inline-header}}

inline的语言意义与编译器是否把函数调用展开不是一回事。多份定义必须满足ODR条件，包括一致的token及相关名字查找；用不同宏配置让各TU看到不同inline定义，可能没有链接错误，却仍非法。

### 2.3 私有副本：不报错不代表保持了语义

匿名namespace使这些实体属于各自TU。它消除了外部重复符号，但first和second会分别把自己的计数从0变成1，得到1、1。

{{odr-local-header}}

TU内部辅助函数适合这种组织；程序级共享状态则不应靠加static或匿名namespace“修好链接”。命名空间作用域的非inline const变量通常也有内部链接，inline const、extern const等条件需分别判断。链接与对象存储期、局部static的初始化次数是不同概念。[链接规则](https://timsong-cpp.github.io/cppwp/n4659/basic.link)

### 2.4 定义存在，但不是声明的那个实体

把普通声明版state.hpp交给a和b，却只链接下面的hidden.cpp，仍不能满足外部increment的引用。匿名namespace里的同名函数是另一个实体。

{{hidden-definition}}

类似症状还可能来自没有链接某个目标文件、声明和定义的命名空间／参数类型不一致，以及C与C++语言链接不一致。先定位缺少的具体符号，不要反复改include顺序碰运气。

## 3 前置声明与完整类型

### 3.1 头文件只暴露拥有关系

指针／引用可以提及未完整类型；定义一个对象、取sizeof、访问成员或执行特定销毁操作，则可能要求完整定义。Pimpl把实现留在源文件中，减少头文件依赖。

{{pimpl-header}}

### 3.2 在实现完整的位置生成销毁操作

Impl在源文件中完整定义，再默认生成析构和移动操作。unique_ptr能持有不完整类型，并不等于它在任何位置执行删除都不需要完整类型。

{{pimpl-definition}}

声明了析构函数后，不能假定编译器仍自动生成所需的移动成员。这里显式声明、在实现完整处默认定义；复制禁止。移动后的value返回0是本例主动设计的接口行为，不是所有移动类型的共同保证。通用对象所有权和复制／移动机制见对应专题，本页只保留分文件条件。[默认删除器要求](https://timsong-cpp.github.io/cppwp/n4659/unique.ptr.single.dtor)

## 4 实现与版本边界

### 4.1 探测具体功能，保持调用接口

设置`-std=c++20`不等于某个标准库版本已实现每项C++20设施；头文件存在也不保证某项接口完整。下面以span为例，探测对应库feature-test macro，同时保留相同的外层函数接口。

{{feature-probe}}

data与size仍须描述有效连续范围；功能探测不替代调用前提。C++17下走指针版本，支持相应span版本时使用span；不以“本机新编译器能过”掩盖最低语言／库版本。头文件依赖由代码自己声明，不依赖别的头偶然间接包含。

### 4.2 模块、C接口与诊断工具

模块是C++20设施，标准库命名模块另有版本和实现支持要求；CMI依赖、构建顺序与编译器格式也与普通头文件不同。不能因为书例使用import std，就把它当作所有C++17参考代码的默认入口。[GCC模块说明](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Modules.html)

extern "C"影响语言链接，不会让STL容器、C++异常和跨库分配释放自动变成稳定C接口。模板定义可见性、显式实例化、C ABI、模块完整构建和跨TU初始化顺序仍有后续分支，本页未把它们当作已经给出完整实现。

编译警告、链接诊断和运行时检测各能揭示不同问题；“没有报错”不能自动证明ODR、对象寿命或并发正确。相关线程对象与同步见[线程与同步](线程与同步.html)，范围和实际核验见[系统研究](../../work/cpp-research-2026-10-26/systems/research.md)。
