这章围绕三个实际判断展开：复制后要不要独立数据，接口是否转移释放责任，失败时哪些状态必须保住。std::move、智能指针和异常安全都服务于这些问题；只记语法名词很容易写出能编译但契约错误的类。代码以 C++17 为准。

1 复制、移动与对象自身的契约

1.1 能直接组合资源，就先不写五个特殊成员

字符串、容器和智能指针已经承担资源管理。只有字符串与 vector 成员的记录类型，通常不需要手写析构、复制、移动；它们的默认操作已经符合按值使用的预期。只有自己额外管理资源或不变量，才需要继续设计特殊成员。

struct Record {
    std::string label;
    std::vector<int> values;
    // 容器已经管理资源；默认复制形成独立值，默认移动交给成员完成。
};
struct CopyOnly {
    CopyOnly() = default;
    CopyOnly(const CopyOnly&) = default;
    ~CopyOnly() {} // 用户声明析构函数，不再隐式生成移动构造函数
};
struct BlockedMove {
    BlockedMove() = default;
    BlockedMove(const BlockedMove&) = default;
    BlockedMove(BlockedMove&&) = delete;
};
struct FallbackCopy {
    BlockedMove member;
    FallbackCopy() = default;
    FallbackCopy(const FallbackCopy&) = default;
    FallbackCopy(FallbackCopy&&) = default; // 因成员而被隐式删除；重载决议忽略它
};
static_assert(std::is_move_constructible_v<CopyOnly>); // 实际可由 const& 复制构造
static_assert(!std::is_move_constructible_v<BlockedMove>);
static_assert(std::is_move_constructible_v<FallbackCopy>); // 复制回退

这里有三个容易混成一句“编译器会自动移动”的情况：

类的情况 用右值构造时发生什么
没有移动构造，但存在 T(const T&) 可能复制；右值可以绑定 const&
明确写 T(T&&)=delete 被删除的候选仍参与决议，可能阻断复制回退
=default 的移动因成员原因被隐式删除 该移动构造被忽略，可能回退复制

所以 is_move_constructible_v<T> 只说明“能用一个 T 右值构造”，不证明调用了移动构造函数。用户声明析构函数会抑制隐式移动；const／引用等成员也可能使赋值函数被删除。决定值语义时把复制与移动构造、赋值和析构一起看，别只补一个 std::move。

1.2 独立复制动态数组：准备新状态，再无异常提交

若类直接保存裸拥有指针，编译器生成的复制只会复制地址，两个对象可能释放同一资源。下面用 unique_ptr<T[]> 负责已分配数组的清理，类自己实现深复制与大小不变量。复制构造先创建完整目标数组，再复制元素；元素复制中途失败，已构造成员仍会自动清理。

template<class T>
class Buffer {
    std::size_t size_ = 0;
    std::unique_ptr<T[]> data_;
public:
    Buffer() = default;
    explicit Buffer(std::size_t n)
        : size_(n), data_(n ? std::make_unique<T[]>(n) : nullptr) {}
    Buffer(const Buffer& other) : Buffer(other.size_) {
        if (size_ != 0) std::copy_n(other.data_.get(), size_, data_.get());
    }
    Buffer& operator=(const Buffer& other) {
        Buffer prepared(other); // 分配、元素复制可抛异常；此时尚未修改 *this
        swap(prepared);         // 无异常提交；旧数据随 prepared 销毁
        return *this;
    }
    Buffer(Buffer&& other) noexcept
        : size_(std::exchange(other.size_, 0)), data_(std::move(other.data_)) {}
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            data_ = std::move(other.data_); // 先释放原来持有的数组
            size_ = std::exchange(other.size_, 0);
        }
        return *this;
    }
    void swap(Buffer& other) noexcept {
        using std::swap;
        swap(size_, other.size_);
        data_.swap(other.data_);
    }
    std::size_t size() const noexcept { return size_; }
    T& operator[](std::size_t i) noexcept { return data_[i]; } // i < size()
    const T& operator[](std::size_t i) const noexcept { return data_[i]; }
};

复制赋值先构造 prepared，成功后才交换：若分配或复制抛异常，目标对象原值保持不变。这就是此处的强异常保证。自复制也成立，代价是仍准备一份新数组；若业务依赖复用容量或元素有特殊赋值成本，可以另设策略，但必须重新核对失败后的状态，不能只为了省分配改成边写边覆盖。

移动构造把指针交给新对象，并把源大小归零；移动赋值还要先清理目标旧资源。这里对自移动选择“不做事”，保证 b=std::move(b) 保留原值。也可以采用临时移动对象再无异常交换的设计，不是每个类都必须写同一条 self 检查；标准库自移动是否保留原值则要看各自契约。这个类明确约定普通移动后为空，这是本类的设计，不是所有 C++ 对象的统一状态。

Buffer<T> 要求元素可以默认构造与复制赋值，并且析构不抛异常。数组分配仍可能失败；下标访问仍要求 i<size()。通常直接用 vector<T> 更合适，这个实现用于看清“谁清理半成品、何时修改原值、移动后不变量”三件事，不替代标准容器。

1.3 std::move 只改变表达式类别

std::move(x) 本身不移动对象；它把表达式转换为可参与移动重载选择的将亡值。之后选到什么函数，才决定真正发生什么。右值引用形参有了名字，表达式依然是左值。

struct TransferCounts { int copies = 0; int moves = 0; };
class TracedValue {
    TransferCounts* counts_;
    int value_;
public:
    TracedValue(TransferCounts& counts, int value) : counts_(&counts), value_(value) {}
    TracedValue(const TracedValue& other) : counts_(other.counts_), value_(other.value_) {
        ++counts_->copies;
    }
    TracedValue(TracedValue&& other) noexcept
        : counts_(other.counts_), value_(std::exchange(other.value_, -1)) {
        ++counts_->moves;
    }
    int value() const noexcept { return value_; }
};
inline void take_rvalue(TracedValue&& input, std::vector<TracedValue>& out) {
    out.push_back(input);            // input 是左值：复制
    out.push_back(std::move(input)); // 显式交出：移动
}
// const TracedValue c(...); TracedValue x(std::move(c)); 仍调用 const& 复制。
// 单独写 std::move(c) 不构造、不释放，也不搬运任何资源。

在通常的 T(T&&)／T(const T&) 组合中，对 const T 使用 std::move 得到 const T&&，不能绑定到会修改源的 T&&，于是仍复制。没有移动构造的类也可能复制。看到“调用了 move”不能据此判断成本已经降到常数。

对标准库对象，移动后通常是有效但状态未指定：可以析构、赋新值，也可以进行满足自身前提的操作；不能假定 string 一定为空，或直接访问可能已空的容器首元素。某些类型另有明确保证，如从 unique_ptr 移动后源指针为空。用户类型则应把自身移动后不变量设计清楚。

1.4 noexcept 改变容器的搬迁选择，不是“能否移动”的开关

vector 扩容要把旧元素放入新存储。如果移动可能在中途抛异常，而且前面若干旧元素已被改动，恢复原数组就困难；若可以复制，保留原数组到复制整体成功通常更稳妥。移动构造真正不抛异常时，用 noexcept 表达这个保证。

struct CopyableThrowingMove {
    TransferCounts* counts;
    int value;
    CopyableThrowingMove(TransferCounts& c, int v) : counts(&c), value(v) {}
    CopyableThrowingMove(const CopyableThrowingMove& x) : counts(x.counts), value(x.value) {
        ++counts->copies;
    }
    CopyableThrowingMove(CopyableThrowingMove&& x) noexcept(false)
        : counts(x.counts), value(x.value) { ++counts->moves; }
};
struct MoveOnlyThrowingMove {
    std::unique_ptr<int> value;
    explicit MoveOnlyThrowingMove(int n) : value(std::make_unique<int>(n)) {}
    MoveOnlyThrowingMove(const MoveOnlyThrowingMove&) = delete;
    MoveOnlyThrowingMove(MoveOnlyThrowingMove&& x) noexcept(false) {
        if (x.value && *x.value < 0) throw std::runtime_error("move rejected");
        value = std::move(x.value);
    }
};
inline void relocation_examples() {
    TransferCounts counts;
    std::vector<CopyableThrowingMove> a;
    a.emplace_back(counts, 1);
    a.reserve(a.capacity() + 1); // 此类可复制，复制可保留原数组直到整体成功
    std::vector<MoveOnlyThrowingMove> b;
    b.emplace_back(1);
    b.reserve(b.capacity() + 1); // 没有复制候选，可能抛异常的移动仍可使用
}

不要把规则简化成“没有 noexcept，容器绝不移动”。不可复制的元素仍可能使用会抛异常的移动构造；在相应标准条款列出的例外下，不能再假定扩容失败必然完全无影响。反过来，随手给内部可能抛异常的移动标上 noexcept，异常逃出时会终止程序，不能靠标注获得正确性。

2 按值返回：直接构造与可选 NRVO

2.1 return T{} 与 return local 不属于同一条保证

C++17 下，返回同类型纯右值可以直接构造最终结果，不要求先造一个临时对象再移动。即便复制、移动都被删除，make_immovable 仍成立；相应析构函数仍须可访问且未被删除。

struct Immovable {
    Immovable() = default;
    Immovable(const Immovable&) = delete;
    Immovable(Immovable&&) = delete;
};
inline Immovable make_immovable() { return Immovable{}; } // C++17 直接构造结果
inline std::string make_label() {
    std::string result = "ready";
    return result; // 允许 NRVO；未采用时再按返回语句规则考虑移动
    // return std::move(result); 会阻止这个 NRVO 候选。
}

返回有名局部对象则可能采用 NRVO，但它是可选优化。没有采用时，函数仍需要满足返回语句的构造规则。不要为了“强迫移动”写 return std::move(result)：它反而破坏原本的 NRVO 条件。返回成员、条件表达式或不同对象，还要重新分析，不能照搬“所有返回都零复制”。C++23 的返回隐式移动规则另有变化，不默认为本章基线。

工厂的返回类型先表达产品语义：独立普通值就按值返回；需要多态独占对象用 unique_ptr<Base>；产品本来就需要共享拥有时再返回 shared_ptr。把所有工厂都改成共享指针，会改变对象的拥有关系，而不仅仅是换一种更方便的写法。

3 独占所有权：从接口看释放责任

3.1 借用、交出与替换是三类接口

调用者只需要读取对象时，接口接受引用或可空指针即可，无须知道对象恰好存放在 unique_ptr 中。按值接受 unique_ptr 表示取得独占所有权；接受其非 const 引用则允许替换调用方的拥有者。

struct Item { int value = 0; };
inline int inspect(const Item& item) noexcept { return item.value; } // 必有对象，只借用
inline int inspect_optional(const Item* item) noexcept { return item ? item->value : -1; }
inline std::unique_ptr<Item> make_item(int value) {
    return std::make_unique<Item>(Item{value});
}
inline int consume(std::unique_ptr<Item> owned) {
    return owned ? owned->value : -1; // 本调用取得独占所有权
}
inline void replace(std::unique_ptr<Item>& owned, int value) {
    auto next = make_item(value);
    owned = std::move(next); // 先创建成功，再替换
}

consume(std::move(owner)) 调用后，源 owner 变空；但指向原对象的其他裸指针不会被“同步清空”。新拥有者何时销毁资源，决定这些观察指针何时失效。传 std::move(owner) 与传 owner.get() 的语义完全不同，后者不转移所有权。const unique_ptr<T> 只限制这个拥有者本身，仍可修改 T；只读对象应由 unique_ptr<const T> 或只读借用表达。

3.2 get、reset、release：取地址、替换与放弃

inline int ownership_operations() {
    auto owner = make_item(3);
    Item* observer = owner.get(); // 不转移；只在 owner 未释放/替换时有效
    int saved = observer->value;
    owner.reset(new Item{4});     // 删除旧 Item；observer 此后不可再解引用
    Item* raw = owner.release();  // 不删除，owner 变空
    std::unique_ptr<Item> adopted(raw); // 将释放责任立即交给新 owner
    // owner.reset(owner.get());  // 错误：会删除仍被记录的同一对象
    return saved + adopted->value;
}

get() 是观察；reset() 替换并清理旧对象；release() 只交出裸指针并停止负责清理。释放责任必须马上有新的承接者，不能把 release 当成“安全删除”。对某个指针置空，只修改这一个变量，无法修复其他别名。不要执行 reset(get()) 后再观察结果，它已破坏所有权。

3.3 释放方式必须与取得方式匹配

文件不是用 delete 关闭，C 分配的内存也不是随意交给默认删除器。把正确清理动作写进拥有者类型，才能在正常返回和异常路径上使用同一套责任关系。

struct FileCloser {
    void operator()(std::FILE* file) const noexcept {
        if (file) std::fclose(file); // 析构路径只清理；错误报告走显式接口
    }
};
using File = std::unique_ptr<std::FILE, FileCloser>;
inline File open_file(const char* path, const char* mode) {
    File file(std::fopen(path, mode));
    if (!file) throw std::runtime_error("open failed");
    return file;
}
inline void checked_close(File& file) {
    std::FILE* raw = file.release(); // fclose 无论成功与否都不应再次关闭
    if (raw && std::fclose(raw) != 0) throw std::ios_base::failure("close failed");
}

删除器可以是函数对象、函数指针或带状态的对象；其状态及大小属于拥有者表示的一部分。make_unique 不接受任意自定义删除器；已有句柄要用匹配的 unique_ptr<T,D> 接管。析构时无异常清理与显式检查关闭结果要分开：这里 checked_close 报告错误，但资源已交给 fclose，失败后也不应再次关闭同一个 FILE*。

inline std::unique_ptr<int[]> make_zero_array(std::size_t n) {
    return std::make_unique<int[]>(n); // 值初始化，元素为 0；配套 delete[]
}
// unique_ptr<int>(new int[n]) 错误：单对象 delete 与 new[] 不匹配。
// 有大小、复制和插入需求时直接选择 vector<int>，不要重复实现容器。

单对象与数组版本不能混用；new[] 配 delete[]。通过基类指针释放派生数组也不是“基类有虚析构就可以”的问题。对有大小、复制和范围需求的数组，标准容器通常直接满足契约。

3.4 C 风格 T** 输出：先接结果，再装入拥有者

C++17 里，unique_ptr<T>* 不是 T**，不能靠强制转换把包装对象的内存布局当作裸指针输出槽。先用真实裸指针接收，再立即交给带正确删除器的拥有者。

using CString = std::unique_ptr<char, decltype(&std::free)>;
inline CString acquire_c_text(int (*acquire)(char**)) {
    // 本例 API 契约：写入 nullptr 或可由 free 释放的指针，失败时也满足此约定。
    char* raw = nullptr;
    int status = acquire(&raw);
    CString owned(raw, &std::free); // 立刻接管，随后抛异常也清理
    if (status != 0) throw std::runtime_error("C API failed");
    return owned;
}
// 不能把 unique_ptr<T>* 强转成 T**。C++23 out_ptr/inout_ptr 是另一种适配接口。

这里特意写清 API 的失败约定：失败时也只返回空指针或可由调用方 free 的指针，所以可以统一先接管再检查状态。真实 API 可能在失败时不修改输出，也可能交回部分资源；适配必须服从它自己的文档。替换已有资源时还要明确旧对象由谁释放，不能照抄新建输出的写法。C++23 提供 out_ptr／inout_ptr 适配，属于另一个版本的接口。

4 共享拥有：对象地址不是控制块

4.1 一份控制块，可以观察不同的子对象

共享指针除了保存一个访问地址，还关联一份拥有关系。对 p.get() 再调用普通的 shared_ptr 裸指针构造函数，会创建另一份控制块，而不是加入原拥有关系；两份独立控制块可能释放同一对象。

struct Document { std::string title; int version; };
inline std::shared_ptr<int> share_version(std::shared_ptr<Document> owner) {
    if (!owner) throw std::invalid_argument("document required");
    return std::shared_ptr<int>(owner, &owner->version); // 指向成员，共享 Document 所有权
}
template<class A, class B>
bool same_owner(const std::shared_ptr<A>& a, const std::shared_ptr<B>& b) noexcept {
    return !a.owner_before(b) && !b.owner_before(a);
}
// shared_ptr<int>(owner.get()) 不是共享原控制块，会造成重复释放。
// get() 比较的是存储指针；same_owner 比较的是控制块关系。

别名构造让返回指针访问 Document::version，但负责保活的是整个 Document。因此两个共享指针的 get() 可以不同，却具有同一拥有者；两个相等的裸地址也不能证明控制块相同。这个成员的地址在 Document 寿命内稳定，不能把同样写法直接用于后续可能重分配的容器元素。

4.2 反向边用 weak_ptr，需要使用时一次 lock

父节点拥有子节点，子节点若也强拥有父节点，就形成无法自行归零的引用环。反向关系采用弱拥有，使孩子可以查询父节点，又不阻止父节点释放。

struct Node {
    int value = 0;
    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};
inline std::shared_ptr<Node> attach(const std::shared_ptr<Node>& parent, int value) {
    auto child = std::make_shared<Node>();
    child->value = value;
    child->parent = parent; // 反向边不延长父节点寿命，避免拥有环
    parent->children.push_back(child);
    return child;
}
inline int parent_value(const Node& node) {
    if (auto owner = node.parent.lock()) return owner->value;
    return -1; // 已过期；不要先 expired() 再假定对象仍存在
}

lock() 要么取得可在当前作用域保活的共享指针，要么得到空指针；“检查过 expired，再稍后取对象”不是同一件事。用过期的 weak_ptr 构造 shared_ptr 会抛 bad_weak_ptr，lock() 则返回空值。控制块的寿命管理也不等于对象内部数据自动线程安全。

4.3 从 this 延续既有拥有关系

class Session : public std::enable_shared_from_this<Session> {
    Session() = default;
public:
    static std::shared_ptr<Session> create() {
        return std::shared_ptr<Session>(new Session);
    }
    std::shared_ptr<Session> share() { return shared_from_this(); }
    std::weak_ptr<Session> observe() noexcept { return weak_from_this(); }
    // 构造函数期间尚无有效的共享控制块；不能在那里调用 shared_from_this。
    // shared_ptr<Session>(this) 同样不是复用既有控制块。
};

enable_shared_from_this 让成员函数取得现有共享控制块，而不是从 this 重新创造一个。它要求对象已经被合适的共享拥有者管理；构造函数执行期间尚未完成这层关联。这里用受控工厂保证来源，不能改成构造函数里启动依赖 shared_from_this() 的注册操作。C++17 的 weak_from_this() 可取得弱观察者，未关联时为空。

4.4 shared_ptr 参数要表达是否保留

class Retainer {
    std::shared_ptr<Item> held_;
public:
    int inspect_or_keep(const std::shared_ptr<Item>& item, bool keep) {
        if (keep) held_ = item; // 只有需要时才增加共享拥有者
        return item ? item->value : -1;
    }
    void set(std::shared_ptr<Item> item) { held_ = std::move(item); } // 总是取得一份拥有权
    void clear() noexcept { held_.reset(); }
};
// 纯观察仍用 const Item& / const Item*；只有“可能保留”才需要看到 shared_ptr。

总要获得一份拥有权时，按值传入再移动给成员，允许调用者选择复制或转移。只有部分分支需要保留时，const shared_ptr<T>& 是合理选择：需要时仍可复制同一控制块，纯观察分支不用无条件增加计数。它不是“shared_ptr 一律按 const 引用传”的通用规则；完全不保留的操作仍用对象引用／指针。

5 多态对象：释放、复制与构造阶段

5.1 基类拥有者与按值切片

通过基类接口删除派生对象时，C++17 的常规设计是 public virtual 析构；若类根本不允许通过基类删除，也可以采用 protected nonvirtual 析构禁止该操作。不能执行一次无虚析构删除，看打印结果“似乎正常”就当成支持的语义。

class Job {
public:
    virtual ~Job() = default;
    virtual std::string kind() const { return "base"; }
    virtual std::unique_ptr<Job> clone() const { return std::make_unique<Job>(*this); }
};
class RenderJob : public Job {
public:
    std::string kind() const override { return "render"; }
    std::unique_ptr<Job> clone() const override { return std::make_unique<RenderJob>(*this); }
};
inline std::string by_value(Job job) { return job.kind(); } // 传派生对象时发生切片
inline std::string by_reference(const Job& job) { return job.kind(); }

by_value(RenderJob{}) 的形参是独立 Job，派生部分已被切掉；by_reference 才保留动态分派。需要复制一个多态对象时，用虚 clone() 返回拥有者，而不是把派生对象塞进 vector<Base>。clone 的两个返回类型都是 unique_ptr<Job>，智能指针模板本身不适用裸指针的协变返回规则。

unique_ptr<Base> 的默认删除器不会自动弥补非虚析构。shared_ptr<Base> 从 make_shared<Derived>() 转换时，控制块能保留具体类型的删除方式；但若先抹去类型为 Base* 再建立控制块，情形又不同。这一特例不应成为接口随意省略虚析构的理由。C++20 destroying delete 的特殊情况不属于本章常规方案。

5.2 构造与析构期间，虚调用只看到当前阶段

struct DispatchTrace {
    std::array<char, 4> calls{};
    std::size_t size = 0;
    void push(char c) noexcept { if (size < calls.size()) calls[size++] = c; }
};
class DispatchBase {
protected:
    DispatchTrace& trace_;
public:
    explicit DispatchBase(DispatchTrace& trace) : trace_(trace) { trace_.push(kind()); }
    virtual ~DispatchBase() { trace_.push(kind()); }
    virtual char kind() const noexcept { return 'B'; }
};
class DispatchDerived : public DispatchBase {
public:
    explicit DispatchDerived(DispatchTrace& trace) : DispatchBase(trace) { trace_.push(kind()); }
    ~DispatchDerived() override { trace_.push(kind()); }
    char kind() const noexcept override { return 'D'; }
};
// 完整构造再销毁：B D D B。基类构造/析构期间不向尚未构造/已销毁的派生部分分派。

基类构造期间，派生部分还不存在；基类析构期间，派生部分已经退出。虚调用在当前构造／析构阶段的类中分派，所以例子依次记录 B D D B。这不是“虚函数在构造函数里彻底不工作”，而是动态类型的阶段受到限制。显式 Base::f() 本来就抑制虚分派；纯虚调用则还需单独判断，不能拿这个正常例子为它兜底。

6 异常：清理半成品，与提交最终状态

6.1 构造失败时，谁的析构函数执行

构造函数体抛异常时，外围对象没有完整构造，它自己的析构函数不执行；已经完整构造的基类与成员会逆序销毁。把资源放进成员拥有者，才能让这条规则真正替你收尾。

struct LifeCounts { int live = 0; int outer_destroyed = 0; };
class LiveGuard {
    LifeCounts& counts_;
public:
    explicit LiveGuard(LifeCounts& counts) noexcept : counts_(counts) { ++counts_.live; }
    ~LiveGuard() { --counts_.live; }
    LiveGuard(const LiveGuard&) = delete;
    LiveGuard& operator=(const LiveGuard&) = delete;
};
class ConstructorProbe {
    LifeCounts& counts_;
    LiveGuard first_;
public:
    ConstructorProbe(LifeCounts& counts, bool fail) : counts_(counts), first_(counts) {
        if (fail) throw std::runtime_error("construction failed");
    }
    ~ConstructorProbe() { ++counts_.outer_destroyed; }
};
// 构造函数体抛异常：first_ 已完整构造，自动析构；~ConstructorProbe 不执行。

ConstructorProbe 失败后 first_ 清理，live 归零，但 outer_destroyed 不增加。如果把 new 出来的资源只保存在裸指针成员，再期待外围析构函数回收，就会漏掉构造失败路径。new T 的构造失败时，分配给 T 本身的存储会释放；它不等于自动回收构造函数中另外申请的裸资源。委托构造中，若目标构造已经完成而委托函数体再失败，完整对象的析构行为又不同，不能把“自身析构不运行”无限推广。

局部拥有者也一样：栈展开清理已经构造的自动对象；不会因为一个裸指针变量离开作用域，就自动对它指向的资源调用删除。正常 return、抛异常、多处分支都使用 RAII，比在每条出口补一遍 delete 更稳妥。

6.2 throw; 保留原异常，throw e; 创建新异常

class DomainError : public std::runtime_error {
public:
    int code;
    explicit DomainError(int value) : std::runtime_error("domain failure"), code(value) {}
};
inline void preserve_error() {
    try {
        throw DomainError(7);
    } catch (const std::exception&) {
        throw; // 原异常对象继续传播，保留 DomainError 和 code
        // throw e; 若 e 是 const std::exception&，按静态类型复制，发生切片。
    }
}
inline int classify_error() {
    try {
        preserve_error();
    } catch (const DomainError& e) {
        return e.code;            // 具体类型在前，避免复制异常对象
    } catch (const std::exception&) {
        return -1;
    } catch (...) {
        return -2;
    }
    return 0;
}

catch(const Base& e) 避免捕获时复制；重新传播用无操作数的 throw;。写 throw e; 会按表达式静态类型初始化一个新异常对象，可能切掉派生字段。具体 catch 写在基类之前；catch(...) 放最后。无操作数 throw 必须有仍在处理的异常，否则会终止程序，不能当作任意位置的“再次抛出上次错误”。

6.3 强保证、基本保证与不抛保证，分别检查什么

保证 失败后要兑现的状态 本章中的落点
强异常保证 对所承诺的对象状态，操作失败等同于没有提交 Buffer 复制赋值先准备，再 swap；地址输入先完整校验再赋值
基本保证 不泄漏，必要不变量成立；值可能已经改变 某些原地修改可以采用，但必须说明仍可进行哪些操作
不抛保证 这项操作不向外传播异常 Buffer 的指针交换、移动与大小更新；前提是组成操作确实不抛

noexcept 声明或 noexcept(expr) 查询的是异常规格，不是对实现的数学证明。要审查内部调用以及析构、删除器的行为。复制并交换的强保证也依赖准备阶段可安全清理、提交阶段不抛；元素复制引发的外部日志或计数变化不一定能回滚，不能把“目标数组不变”扩张成“全世界状态不变”。

析构函数应完成不抛清理；默认异常规格还会受到基类、成员析构规格的影响，不能只看自己写的函数体。若析构期间又有异常逃出，尤其在栈展开时，就可能触发终止；改成 noexcept(false) 不是一般性解决办法。需要上层处理的保存、刷新、提交、关闭错误，应提供显式接口并约定失败后的资源状态；本章的 checked_close 就是在析构兜底之外增加错误报告通道。外部 I/O 已产生的效果，也不可能仅靠交换两个内存对象自动撤销。
