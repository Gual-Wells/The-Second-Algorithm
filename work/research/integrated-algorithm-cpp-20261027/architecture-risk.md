# 算法与 C++ 实战整合：内容架构、装配与导航风险

本轮实际核查：2026-10-27 至 2026-10-28。代码基准为 `main@90a59c8507f6c17f7aad737317deef011ad6604c`，另有上一轮未提交研究。本分支只读现有代码和数据，唯一新增文件为本研究稿；没有改协议、教材、测试、数据库或部署，没有执行构建、安装或重新跑测试。

研究采用用户的新前提：算法与 C++ 实战合并建设，比较手写与标准设施的实现路径，停止独立 C++ 生产线；旧实现、ID、版本资源可作为测试材料整体抛弃。以下不提出旧 ID 映射、旧笔记迁移、兼容旧客户端、双写或保留旧试稿数量的要求。“仍需要某项能力”指新系统的正确性要求，不是要求维护旧版本。

**判断：可以采用轻结构，但需要改变内容身份和实现验证的组织；只合并两个界面入口不够。** 当前的静态内容、确定性构建、源码区域标记、浏览器阅读和独立结果对照都可以用来实现新方案；没有证据支持先引入数据库内容库、微服务、知识图谱或付费检索。另一方面，“章节里出现了两个代码块”不能代替两条实现路径，“全文能搜到一个 C++ 名词”也不能代替可恢复的机制研究。

## 1. 当前实现实际把什么当作对象

以下是读取源码得到的现状，不是从架构文档推测出的理想结构。

| 层次 | 实际实现与限制 | 对新架构的影响 |
|---|---|---|
| 出版登记 | `carrier/publications.json` 是 `collections[] → documents[]`；collection 必须为 `algorithm/cpp` track，chapterNumber 按 track 唯一；document ID 全局唯一，同一 authority path 禁止重复登记 | 必须去掉两条生产线的硬约束；collection/多篇文档这一轻结构本身仍可用 |
| 作者稿与代码 | 一篇固定为同目录、同名 `.source.md/.cpp/.md/.html/build/*.json`；path 校验只接受 `content/<unit>/<name>` | 可以承载一个主题的两个实现，但不能直接引用另一篇的权威区域或任意源文件组合 |
| 代码区域 | `// BEGIN id`/`// END id` 被抽取为字符串；一篇中的所有区域必须在该篇恰好引用一次 | 区域是显示定位，不包含“解决什么问题、哪条路径、适用条件、最低标准、能否独立提交”等语义 |
| 参考位置 | pattern 只有一份 `canonical` 对象，里面放 document/anchor/code/symbols/code_blocks | 可以表示主要讲解位置，却没有一等的实现变体及其验证目标 |
| 研究检索 | Python search 查询 sources/cases/patterns/books/inventories，按记录文本和 topic alias 展开 | 不会自动读取教材正文，也没有 C++ 机制对象或实现依赖检索 |
| 读者检索 | web 从已发布 document HTML 中逐篇提取文本，按 H2/H3 分段匹配；册级查询先按 track 过滤 | 接口名和任务名有可能命中，但不存在“同一机制出现在哪些题、哪条实现、哪里主讲”的结构保证 |
| Worker/数据库 | `/api/library` 读静态 catalog；D1 只存凭据／会话／通用 reader_state，没存 track、算法、模式、题目或代码内容 | 合并内容线不需要因此重做后端数据模型或把正文搬入 D1 |

证据定位：[出版校验及路径约束](../../../scripts/build-carrier.mjs#L28)、[作者权威与代码区域校验](../../../scripts/build-carrier.mjs#L71)、[当前登记](../../../carrier/publications.json)、[pattern 校验](../../../second_algorithm/catalog.py#L69)、[研究 search](../../../second_algorithm/catalog.py#L189)、[web search](../../../web/app.js#L425)、[Worker](../../../server/worker.mjs#L56)、[D1 表](../../../migrations/0001_owner_state.sql)。

有两个容易误读的细节：

1. 当前 pattern 记录虽然带 `code_blocks`，Python validator 实际只检查代码文件存在、HTML anchor 存在、symbol 的函数式文本能匹配；没有验证这些 code block ID，也不验证实现合同、编译版本或测试映射。字段存在不等于关系已经受到工程保护。
2. carrier renderer 允许作者稿中原生 fenced code，另以 `inlineExamples` 校验字节。这些例子不会因此自动成为经过编译的参考实现。页面上的 C++ 高亮和复制按钮也不区分完整程序、片段、错误示例或不同版本。

## 2. 删除 track 是有边界的改动，不是完整架构答案

当前 track 在以下地方硬编码：

- `scripts/build-carrier.mjs:44–56`：仅允许两种 track，章号以 track 为键；输出 catalog 也带 track。
- `web/index.html:26–28`：固定算法/C++ 两个 tab。
- `web/app.js:8,15,39,188–198,217,247–248,275–284,769–772`：默认线、两套 shelf、路由归一化、目录过滤、续读与搜索范围都依赖 track。非 read 路由的 collectionId 只要不是 cpp 就被当作 algorithm，不能只新增一个标签期待它自动工作。
- `test/carrier-build.test.mjs:69–109,227–277`：直接断言旧 trial ID、3/7 篇、173 块及两线分别编号；浏览器测试也断言两线搜索隔离和旧材料行为。

新实现可以采用一个统一内容入口、一个阅读顺序，或在统一入口提供题型／操作／机制等检索视图。没有旧兼容要求时应直接采用新 schema 和新测试，删除依赖旧材料数量、旧 ID 及双线规则的断言。无需为了让旧测试继续绿而在新 schema 留一个虚假的 track，也无需把旧 cpp 记录全部改标为 algorithm 来伪装完成。

仍应检验新内容的身份唯一、合法路径、链接可达、源码字节对应、渲染安全和鉴权边界；这些是新系统自身的性质。[当前构建回归](../../../test/carrier-build.test.mjs)、[浏览器回归](../../../scripts/check-carrier-browser.cjs)、[SW 路径与身份保护](../../../web/sw.js#L54)。

## 3. 轻结构最低限度要区分的四类对象

不需要把每个名词都建表，但不能让四种不同事实共用一个“块已完成”状态。

| 对象 | 它负责的事实 | 最小关系 |
|---|---|---|
| 主题／阅读单元 | 当前围绕什么目标、条件、方法和实现组织讲解 | 关联题目、实现和机制；有标题、入口与阅读顺序 |
| 题目／实际任务 | 原目标、输入输出、允许修改、约束和来源是什么 | 一个题目可支持多种方法和实现；题意不同不能因函数相似被合并 |
| 实现路径 | 具体怎样兑现任务；手写哪一步、调用哪项标准设施，结果和成本受哪些条件限制 | 指向唯一源代码、所依赖的支持代码、标准版本及实际验证目标 |
| C++ 语义单元 | 哪个类型／库合同决定实现可用；在哪些条件下成立、哪里有主讲和实例 | 可被多个实现引用；有可检索别名、出处／版本和已研究／未决边界 |

例如“首个不小于目标的位置”可有手写边界收缩、`std::lower_bound` 两条实现。二者共享一份行为合同与测试集合，但有不同实现身份；`set::lower_bound` 又因存储结构与总成本不同，不应仅换一行就算同一实例的等价实现。比较器方向、迭代器能力和 end 的解释是可复用的语义单元；某篇中的 `BEGIN lower` 只是其中一段源码的定位。

“手写／标准库”应记录本次要比较的操作层次：手写二分仍可使用 vector；自己维护单调队列仍可使用 deque。不能把“手写”误定为完全不碰标准容器，也不应为了满足双路径数量，给每个题型强行找一个低价值替代解。

这些身份可以放在一份主题 metadata 加一份小型机制索引中，不要求四套数据库。标题、文件路径和标题生成的 slug 不宜同时承担语义身份；新内容未来改标题、拆成两篇时，仍需要知道哪个实现和哪个合同受影响。这是新系统持续修改所需的身份，不是旧 ID 迁移。

可采用的轻量表达示意如下；它说明需要表达的关系，不是本次已经确定的 schema：

```text
topic: boundary-search
  tasks: [某原题或明确的内部任务]
  implementations:
    manual-first-ge → contract:first-ge, source:file#region, tests:...
    std-first-ge    → contract:first-ge, source:file#region, tests:...
  semantics: [partition-for-lower-bound, iterator-cost, past-the-end]

semantic: iterator-cost
  aliases: [随机访问, iterator, lower_bound, distance]
  primary: 当前统一阅读库中的一个位置
  occurrences: 从 implementation 引用派生
  research: 已核查的版本/出处/范围，或者具体未决问题
```

实现关系在一个地方编写，反向出现列表和检索索引从它生成；不要在 pattern、主题、作者稿、代码注释和测试清单分别手工维护同一张表。也不需要给每个 int、for 或单个 API 重载建语义卡，只有影响实际判断、可复用或尚未解决的合同值得登记。

## 4. 单权威代码：先分清“源码、显示区域、验证目标”

当前 `tools/build_handbook.mjs:11–21` 适合一个稿名对应一个源文件，按 marker 插入代码；`scripts/build-carrier.mjs:71–103` 再校验字节和区域顺序。这个基础并不妨碍一篇同时讲手写与库版本。若它们都能自然放入一个 `.cpp`，且每段各主讲一次，**首个新主题无需先改成通用代码仓库**。

真正需要松开的不是“所有代码必须拆得更碎”，而是把代码块误当成完整实现的假设：

- 一个实现可能依赖类型别名、结构体、helper、头文件和平台 adapter，涉及多个区域。
- 一个区域可能包含多个互相关联的函数，或同时支持多个实现；不宜为了每函数一 ID 强拆完整上下文。
- 主文展示的局部片段、可直接编译的解答和用于反例的错误代码，具有不同交付合同。
- 同一段已验证源码在另一个任务中需要引用时，显示副本应从同一源生成或链接；不能靠复制后分别维护。

因此最小新增物应是**声明的实现／验证目标**：标明入口、源码区域或源文件、必要支持、标准模式及预期结果。简单目标可隐含使用本主题 `.cpp`；只有实际需要跨文件或组合导出时才声明 dependencies。物理区域 marker 可以继续使用，不需要立刻引入 C++ AST 自动改写、自动推导 include 或复杂模板引擎。

一旦引入共享依赖，构建身份必须覆盖实际依赖闭包和装配配置，而不只覆盖同名 `.cpp`：共享 helper、头文件、目标版本或 adapter 改变后，受影响的导出与验证记录都要重建。当前 `readAuthority` 的五项输入摘要适合当前单篇模型；不能未经扩展就拿来给新组合产物背书。若为新内容增加目录层级，也须同步更改 `contentPath` 和 `CONTENT.glob("*/*.source.md")` 发现规则，防止新稿在更深目录静默漏检；目录变深本身并非新架构的必需条件。

一旦提供“完整答案”复制／下载，必须从该目标的实际依赖生成并独立编译，不能以“整本 `.cpp` 被测试 include 过”为证据。上一轮研究 runner 已展示从正式区域抽取内核后装配 `main`／Solution 的办法；它是原型，不是当前通用作者系统已经拥有的功能。[原型 runner](../algorithm-cpp-implementation-20261027/run_probes.py)。

若以后确实需要跨篇重复显示同一区域，当前“一篇全部块各一次”的约束可改为“每个显示实例指向一个源码区域，区域只有一份权威；实例锚点独立唯一”，同时保留缺块／重复 ID／链接完整性检查。**暂时只是链接到主讲位置时不必提前放宽。**

对有意错误或只说明局部语义的例子，可允许作者稿短片段，但应明确它的角色；它不能被当成已验证完整解答。需要编译诊断的例子声明 expected compile/link failure，且不执行无效程序。当前独立编译探针、多 TU 工具已有这种能力模型，可以在新目标中使用相同原则。[编译探针](../../../tests/cpp/verify_object_interfaces.py)、[多 TU 核验工具](../../../tools/verify_cpp_systems.py#L69)。

## 5. 双路径测试不能退化为“两份代码输出相同”

两份实现共享同一错误时，互相对照仍会通过；有多个合法输出时，直接比较输出文本又可能误报。要先决定它们共享哪份合同：

- 输入域、空输入、重复值、负数及极值；是否允许排序／修改输入。
- 是任意最优解还是固定平局规则；区间开闭、稳定性、结果顺序及无解表示。
- 最低语言／库版本，标准设施是否允许，复杂度针对什么操作计数。
- 输出值之外的状态要求，例如输入未改、按迭代器只删除一份、持有的借用是否仍有效。

再据该合同选择朴素枚举、已知独立模型、性质检查、适配器样例及类型／诊断探针。手写与库路径可以共用任务的测试数据，但要分别进入真正的编译和运行目标，不能让其中一个仅在 `#if` 中被旧标准跳过。

当前值得借鉴的实现事实：

- `tests/cpp/contiguous_ranges_test.cpp` 直接 include 权威 `.cpp`，另写枚举模型；不是把参考实现复制到测试中作为 oracle。
- CI 默认枚举 `tests/cpp/*_test.cpp`，均以 C++17 编译；20/23 只额外运行几个硬编码文件。新注册一个 20/23 目标不会自动进入这些分支。
- `verify_object_interfaces.py` 区分编译失败与成功后运行；`verify_cpp_systems.py` 区分 compile/link/run，并能按源码区域组成多个 TU。

证据：[连续片段独立模型](../../../tests/cpp/contiguous_ranges_test.cpp#L1)、[CI](../../../.github/workflows/validate.yml#L43)、[编译探针](../../../tests/cpp/verify_object_interfaces.py#L33)、[分阶段核验](../../../tools/verify_cpp_systems.py#L109)。

需要改变的是“哪些声明实现已被什么检查覆盖”的发现方式，避免依赖文件名和人工名单；不是强制每条实现都运行全部 sanitizer、全部编译器和巨量随机测试。版本、目标、输入范围和结果应可追溯；构建哈希只证明字节身份，不能认证手写路径忠实实现了考查机制，也不能认证语义完备。

## 6. 停止独立 C++ 线之后，怎样避免机制消失

最具体的风险不是失去旧的七份文件，而是研究入口变得不可见：一个生命周期规则在三个算法主题中各出现两句，未来遇到相关编译错误时不知道哪里已经研究、哪里只是提到；或者因为算法章暂时没有承载位置，就把未解决的 C++ 问题自动当作已排除。

轻量恢复机制可以是统一内容研究中的一份语义索引：

1. 记明确问题和有区分力的边界，例如“插入可能 rehash 后是否还能用原 iterator”，不是笼统记“会 unordered_map”。
2. 对已承载问题指向一个主要讲解与相关实现；对只有提及／尚未核验的保留未决问题与出处。
3. 状态区别“来源已取得、规则核查过、有正文、有实例、哪种验证实际完成”。不能因为一段代码出现某 API 就把整个机制记完成，也不以脚本认定语义覆盖。
4. 当前算法主线用不到的语言问题可记候选、暂不纳入及理由；以后由具体实作／修错任务重新打开，而不要求每个算法章先补齐 C++ 全目录。

这不是恢复独立 C++ 生产线。机制索引是一种定位和研究视图，可以指向算法章的节、实际修错任务或统一参考页；它不独立规定章节进度、第二套编号、第二套代码权威或自动追加课程。未来若要补 C++ 漏洞，可以从实际问题和上述未决项恢复，重新取证并形成具体任务，不需要依赖已经被抛弃的旧版材料。

当前 `catalog/scope.json.cpp_discovery_entries` 只列宽泛入口，`patterns.jsonl` 有机制候选但没有上述分维状态和实现关系；`catalog.py report` 的 open-pattern 列表也不能代替这些事实。新方案可以重定当前轻量记录职责，不必为了保留这些对象名而沿用旧数据，也不必一次性建立完备 C++ 本体。

## 7. 读者导航与研究检索要用同一关系，呈现不同视图

统一主阅读顺序应围绕任务的目标与条件。题型、操作、数据结构、C++ 合同及 API 别名是进入同一内容的入口，不应再各复制一册正文。一个具体例子是：读者按“有序后继”进入任务，按 `lower_bound` 找到手写／库实现及容器差异，按“迭代器成本”找到主讲和其他适用处；三条入口应落到同一组真实位置。

当前读者检索有两个实际限制：

- 为查询循环加载每篇 HTML，再取 H2/H3 区域文本；没有使用 catalog pattern/semantic 信息。没有下载或请求失败会显示范围，这一诚实边界适合新系统继续具备。
- 每篇只有一个 `sourceUrl`；下载当前 collection 时取 document JSON 与整份 `.cpp`。代码块复制只取当前 `<code>` 文本。它们现在没有表达某条实现的独立源码包或依赖集合。

证据：[search](../../../web/app.js#L425)、[源码展示](../../../web/app.js#L561)、[离线下载](../../../web/app.js#L587)。

初期可保留 HTML 分段全文搜索，增加由真实内容关系派生的别名／目标位置和简单过滤；若语料增长后出现明确的下载量、延迟或离线范围问题，再生成静态检索索引。它可以继续随内容版本打包，不需要检索服务或向量数据库。不能仅把“会查不到”换成未验证的“语义搜索会解决”。

新内容的主要目标位置建议有显式锚点或确定的语义地址；当前自动从标题生成 slug、重复标题加序号的规则，适合普通 TOC，不宜成为所有机制引用的唯一身份。标题改变或在前方增加同名标题都可能改变引用结果。构建仍须检查当前产物内的所有链接和锚点，不涉及兼容旧地址。[标题锚点生成](../../../tools/build_handbook.mjs#L40)、[当前链接目标验证](../../../scripts/build-carrier.mjs#L242)。

如果后来导出 `.hpp`、多文件压缩包等，改动不能只在作者构建器：当前 SW private URL 只允许本构建白名单中的 json/cpp/md，`libraryPaths` 和 downloadCollection 也按当前导出类型枚举。新资产必须进入同一受保护的发布清单及离线路径验证，不能塞到公开 assets 目录绕过它。[SW](../../../web/sw.js#L54)、[路径枚举](../../../scripts/build-carrier.mjs#L263)。

## 9. 可验证的验收条件

建议用一个小型新语料验证结构，先覆盖至少两个真实任务、一组有意义的手写／标准路径和一个跨任务重复使用的 C++ 合同；这些数目只是架构 fixture 的最小形状，不是章节或内容覆盖配额。

1. **统一内容入口成立。** 当前 catalog、页面与读者操作不依赖 algorithm/cpp 两种 track；新增主题无需改一串 track 分支。没有为旧 ID/旧版本留下占位或双写。
2. **关系可以查明。** 从一道题能找到其条件及所有已声明实现；从一个实现能找到源码、版本、合同和测试目标；从一个机制能找到主讲及使用它的任务。没有把缺失关系填成不存在的未来章节。
3. **单权威装配成立。** 修改一处源码后，相关显示与导出由它重建；故意改派生产物会失败。若声明独立答案，该答案必须脱离整本源文件独立编译，缺 helper/include/类型定义不能被其他主题偶然补齐。
4. **两条路径都真的验证。** 两个实现分别执行，按共同的行为合同和独立模型检查边界、输入修改及合法输出性质；不同标准分支有对应真实实例化，跳过不能写成通过。
5. **机制状态不虚报。** 加入一个仅有出处、尚未研究的问题时，报告能显示未决而非已覆盖；正文提到 API 不自动完成整个机制；研究部能从具体未决项恢复下一步。
6. **检索和导航指向当前权威。** 按任务词、API 别名及合同词查询可落到正确位置；改标题仍能发现当前有效的主要位置；断链／重复 ID 构建失败。当前离线范围不足如实显示，不能报成无内容。
7. **读者可区分复制对象。** 主文代码片段与“完整答案”名称相符；错误示例、版本替代和局部片段不伪装成同一种可提交代码。代码原生选择、横滚、复制后的原字节和字号可用性仍需浏览器核验。
8. **安全与运行边界独立通过。** 新发布的正文、源码、检索索引及新增导出都进入鉴权和明确路径清单；不泄漏研究原件／本地文件。正文仍是静态产物即可，不因合并内容线强制新增数据库、后台或持续费用。

其中内容归并、手写实现是否绕过核心考查、适用条件和语义是否讲清，仍需要真实审阅；validator 只能检查可机械验证的关系和字节，不能产生“全 C++ 查漏完成”认证。

## 11. 新增明确要求：全项目唯一的 C++ 问题编号与主讲解

2026-10-28 用户进一步明确：自己的 C++ 知识不足，手写和库实现涉及的知识需要全项目问题编号唯一的讲解，便于日后学完算法后补 C++。这把前文“可恢复的机制索引”提升为新内容的明确要求；不能只挂几个 API 标签，或假定读者已经掌握其中的语言机制。本节仍是方案研究，没有创建编号库或改写正文。

### 11.1 编号标识一个可解释的问题，不标识章节、题号或代码块

建议采用 `Q000001`、`Q000002` 等**项目全局唯一、无主题含义的编号**。六位只是可读的最小显示宽度，可按需增长，不应把 999999 当作内容上限；不要另分算法册／C++册编号，也不在换章时重新从 Q1 开始。外部算法题 ID、实现 ID、代码区域 ID 各自负责不同事实，不能冒充 Q 编号。

每个 Q 应当能回答一个具体的“为什么／怎样写才成立／什么条件下会错”的问题，其粒度由触发条件、决定规则和修复选择共同确定。例如：

- “reserve 后为什么还不能按下标写入 n 个元素？”与“push_back 后原来的引用何时失效？”虽然都涉及 vector，仍是不同问题。
- “为什么把 int 乘积赋给 long long 还可能溢出？”可包含先扩宽的解释和边界例子；`accumulate` 初值决定累加器类型可以作为另一个具体问题，关联前者，而非每出现一次数值代码都重新编号。
- 手写二分和库二分共同需要的区间、迭代器及比较方向知识，可分别指向相同 Q；不把某一个 `lower_bound` 函数名当成能够包住所有合同的大问题。

不要求给每个 token、每个重载或每一行代码建卡。一个问题的紧密版本差异和必要反例可在同一 Q 下用局部子标题组织；能独立造成错误、需要不同判断或修复的合同宜分开。遇到同名但条件不同的问题，需要实际比较后决定合并或拆分，不能让去重脚本替代语义判断。

### 11.2 一个 Q 一份权威主讲解，首次需要时就近讲清

建议用一份轻量问题登记记录 `Q → 标题／别名／主要正文位置／适用版本／相关实现／证据与未决项`。**权威讲解仍可直接写在首次需要它的算法主题正文中**，不必把连贯的正文拆成几百个独立卡片文件；登记只指向这一处原稿及显式锚点。编号不由标题 slug、章号、文件名或代码块序号生成。

首次在主阅读顺序中依赖某项知识时，应在相邻思路和代码处标明 Q 并给足当前实现所需的解释，不能只放一个“详见某个未来 C++ 章节”的链接。后续遇到同一问题，用该 Q 引用主讲解，同时保留当前题目必要的适用条件和本次实现选择，不再另写一份可漂移的完整定义。

用户随后又明确“只需要一次讲解就行”。因此同一 Q 在阅读正文中只完整讲一次；后续只显示编号、简短标题或链接，必要时跳转到原处并可返回当前任务，**不默认重复内联、自动展开或重新装配完整解释**。即使复用的是同一源字节，重复显示完整讲解也不符合这一阅读要求。主讲后来补充或调整时，所有引用仍指向该 Q 的当前唯一位置。主题移动、主讲位置调整或代码分块变化不应迫使问题换号；这针对新内容持续建设，不要求承接任何旧资源的 ID。

主讲内部可包含讲清该问题必需的实例和反例；后续算法任务仍可有自己的应用代码，但仅编号引用该知识问题，不重新教学。只有发现实质不同的新语义问题才分配新号；换题、换实现或再调用同一 API 不产生新号。原解释不充分时补充原处，不在后文另起一份解释。

### 11.3 问题与代码实现形成多对多关系

一条手写／库实现可关联多个 Q，例如数值类型、参数借用、比较器和迭代器失效；一个 Q 也可关联多个题目和多条实现。关联应写在实现或问题记录中的一个权威位置，另一方向由构建派生，不在两份清单中手工同步。

源码区域仍负责显示，验证目标仍负责实际编译／运行，Q 负责知识问题。不能规定“一块代码就是一问”，也不能规定“一问只能对应一段代码”。代码注释或正文可标 Q 入口，但完整解释不应同时维护在注释、主题正文和补 C++ 页面三处。

登记的最低事实建议是：编号、问题标题和检索别名、主要解释的原稿位置与锚点、对应的已声明实现、版本及证据位置。复杂的知识先修图可以以后据真实问题增加；当前不需要为所有 C++ 概念先造完关系网。对知识不足的读者，作者仍须核对本段代码实际依赖的前置问题是否已经讲清，不能仅靠“登记齐了”认证自包含。

### 11.4 编号存在、讲过和验证过要分开，用户掌握另行判断

问题登记应保留哪些规则和版本实际核查、主讲是否存在、哪些例子／诊断真正验证、还有什么问题没有解释清楚。可用少量明确字段或状态组合表达，不需要仪式化表单。

一个 Q 只有线索或已研究但未写解释时，可以留在研究视图，不能自动算已讲解；主文依赖了尚未解释的 Q，就应作为当前内容缺口处理。不能用一个空锚点、API 名称、测试通过或“以后补 C++”关闭它。某一测试只支持其具体目标，不代表该 Q 的所有条件和标准版本都已证实。

这些是**内容供给与证据状态**，不是用户学习状态。编号、被阅读、读到末尾、练习运行成功，均不自动证明用户掌握；未来是否另设个人复习／作答记录可独立决定，不应改写问题本身的研究状态。

### 11.5 未来补 C++ 是同一问题库的视图，不是重写一册

学完算法后，可以按类型与转换、调用与借用、容器与迭代器、比较与数值等机制，或按“全部 Q／只有提及／尚未解释／有练习”等事实组织同一问题集合。每行保留 Q、主讲、涉及题目与实现、已核查边界和相关练习；点击后仍到同一权威答案。主题词和 API 别名负责发现，Q 负责确切定位。

这一视图生成静态目录和链接即可，按知识关系索引已有的唯一解释，不能默认再拼成一册重复讲解。它不要求重新建立独立 C++ 生产线，也不预设所有 C++ 机制都已经被算法任务覆盖。后续发现实质不同的新语义问题才新增编号并研究，相关实例仍链接到真实实现。

### 11.6 多 Agent 并行时，采用单写者批量定号

不建议多个 Agent 分别读取当前最大 Q 再加一，也不为编号建立中央服务、远程数据库或审批。简单办法是：

1. 分工前读取当前问题登记；已知问题直接复用正式 Q。每个 Agent 对新候选使用只在工作稿中出现的确定性临时键，例如 `draftq:<任务>:<Agent>:<局部名>`，避免抢写全局登记。
2. 整合 Agent 作为本次唯一登记写者，实际比较候选的条件和规则；相同问题归到已有 Q 或同一新候选。语义归并是内容工作，不是自动字符串去重。
3. 将剩余新候选按临时键排序，从登记的下一个可分配号依次批量赋号，生成一次映射并更新工作稿引用。相同基线和候选集合可得到相同分配；后续批次继续递增。
4. 发布构建拒绝重复 Q、未解析临时键、悬空主讲、无效锚点及冲突的主讲位置；若另一个工作进程已改登记，整合者重新读取再分配，不能覆盖已有号。正常编号整合无需向用户逐问确认。

这里的“唯一写者”是一次整合职责，不是新常驻服务或审批层。它只序列化登记和引用替换，内容研究、例子及实现仍可并行。尚未完成解释的问题有明确未决状态；已形成正式新知识库后，不因重排章节随意重编号或把一个号换给另一问题。

补充验收条件：同一知识问题在两个任务和两条实现中复用同号，主讲只有一份且阅读中只完整讲一次，后续只有编号引用／跳转；修改权威解释后各入口一致；新增两个并行候选经整合不冲突；只有线索的 Q 能在研究视图查到但不被报告成已解释；未来 C++ 目录能直接由同一登记生成且不复制讲解；所有展示／阅读进度均不被称作用户掌握证据。本轮只形成这些建议，未分配任何正式 Q。
