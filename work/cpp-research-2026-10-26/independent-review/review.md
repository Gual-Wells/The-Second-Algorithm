本次先把七份作者稿及七份代码的 SHA-256 固定到 [baseline.json](baseline.json)，再读取未参与本轮目录构造的 LLVM libc++ 官方回归材料，独立分析机制，最后检查现稿承载。独立指本轮建设材料隔离，不是声称模型训练中未见过这些问题，也不是用五份测试代表整个 C++。

## 实际读件与方法

[actual-reads.json](actual-reads.json) 保存五份真正读取的原始 URL、版本标签、字节摘要及范围。上游代码在被忽略的本地目录保留；没有把测试文件或其辅助 harness 拷进教材。LLVM 上游测试自身没有在本机完整构建；下面运行的是独立编写的本项目反例与回归。两个猜测路径返回404后，使用实际目录API找到有效路径，失败没有写成无相关内容。

| 外部读件 | 先独立得到的关键机制 | 对本轮现稿的挑战结果 |
|---|---|---|
| optional/object/assign/copy | 已有值→空会销毁对象；空→值需要复制构造，失败保持空。单个 optional 的保证不自动保全外围多个槽及计数的关系 | 触发复查 ring 复制赋值，发现真实不变量缺陷，见下文 |
| vector/cons/exceptions | 构造体内部的元素构造、迭代器操作及分配器都可能失败；清理已经完成的资源是构造路径的职责 | 对象与资源中的 Buffer 准备／提交、构造失败成员清理已提供主要承载；定制 allocator、完整自制 vector 的细节仍为扩展，不能称该上游测试每个配置已覆盖 |
| filter/begin | 惰性不等于每次 begin 都重扫；forward_range 的首次匹配会缓存，单遍 input 情况不同 | 原稿没有明确这个区别，已由根补短段；独立 C++20/23 检验实际谓词调用次数 |
| variant/assign/copy | 同 alternative 可调用元素赋值；切换 alternative 可能构造新对象；异常后有 valueless_by_exception 路径；某些路径先准备临时值以保住旧值 | 当前没有完整 variant 作者稿，属于实质待补；不能由使用 optional、讲了 RAII 或提到异常保证就算已经讲解 |
| debug sort invalid comparator | 不自反还不够；非对称、顺序传递及不可区分关系传递都重要；普通浮点 `<` 混入 NaN 会破坏最后一项 | 原稿只用 `<=` 反例，判别条件不足；根补四性质及 NaN 后置比较器，由新测试检查关系后才合法排序 |

以上是五份独立读件及机制对照，不是五道刷题题目，也不是从它们推导的面试频率。

## 已验证的真实缺陷：覆盖 ring 的复制赋值

初稿 `overwrite_ring` 使用默认复制赋值：先对 `vector<optional<T>>` 逐槽赋值，再更新 `head_`、`used_`。虽然本类要求 T 的移动构造不抛，复制构造仍可抛。

取容量3：源有效槽为 `{2,0}`，目标有效槽为 `{0,1}`。逐槽复制先更新槽0，再因源槽1为空而清除目标槽1，最后在构造槽2时抛出。目标旧计数仍是2，但实际只剩一个有效对象；下一次合法-looking迭代或pop可能解引用空 optional。

根在独立审阅代码时也发现了同一个问题；这是共同发现，不独占归因于外部挑战。反查用 LLVM optional 赋值状态转换进一步说明了具体失败机制。

- 修复前独立反例：[ring-copy-reproducer.cpp](ring-copy-reproducer.cpp)。只比较存活对象计数与公开 size，不执行失效槽解引用，避免靠运行 UB “证明”缺陷。GCC 16.2 / C++17 观察到 `alive=3 logical_total=4`，断言实际失败。
- 根修复：先完整复制 `prepared`，成功后以不抛交换一起提交槽位、head和used，原目标在准备失败时保留。
- 回归：[cpp_ring_exception_test.cpp](../../../tests/cpp/cpp_ring_exception_test.cpp)，涵盖上述抛异常布局、源／目标原值、成功复制、自赋值、覆盖后逻辑顺序、移动后对象恢复赋值与最终资源归零。
- 同一回归还验证 NaN 后置比较器的四性质（有限样本穷举三元组，包含 NaN、±0、±∞），只对合法比较器排序；C++20/23 下验证 forward filter 的重复 begin 缓存及重建后重新求值。
- 本次实际执行 C++17、20、23 三种编译模式，使用 `-O2 -Wall -Wextra -Wpedantic -D_GLIBCXX_ASSERTIONS`，三种模式均编译运行通过。

旧反例源文件保留为“修前失败输入”；修后再次运行应通过。它不再是尚未暴露给建设阶段的保留挑战。

## 新缺口与限界

需要把 variant 的带标签返回／访问／异常状态作为新候选展开，最好结合解析不同结果或事件分派这类实际代码，不应临时塞几条术语声称闭环。定制分配器与复杂容器构造失败也没有因 Buffer 示例而全部完成。

这轮未审查所有线程交错、所有字符编码、所有 C++20/23 库实现，也未证明每份长文逐句正确。已读的具体案例可用于修改现稿；未读范围保持未知。不存在“反查通过，因此 C++ 范围完备”的结论。
