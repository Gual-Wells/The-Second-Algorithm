# 工程组织与数据关系

客户阅读载体见 [READER.md](READER.md)：Pages壳/版本化正文、独立Worker/D1身份与状态，展示登记共享原有作者稿，不另造内容权威。

第二算法把全局研究、内容工程与参考总册分开组织。共同规则以 [CONTENT_PIPELINE](../protocol/CONTENT_PIPELINE.md) 为准，上游判断见[研究部协议](../protocol/RESEARCH_DEPARTMENT.md)，分线执行见[算法协议](../protocol/ALGORITHM_TRACK.md)和[C++协议](../protocol/CPP_TRACK.md)；本文说明现有工程怎样承接这些职责，不代替内容协议。

## 数据流

```text
全部已知资料基座 + 当前研究／候选稿 + 真实已发布内容
    ↓ 研究部全局梳理、候选比较与实际深读
问题群及动态范围 ↔ 新资料可增补、缩减、拆并或改变主题
    ↓ 在同一工作记录中交接有版本的明确研究目标
算法工程线                      C++工程线
    ↓ 各自深入内容、实现、编写、反查与核验
    ↕ 范围新证据反馈研究部，目标修订后继续
一章的可用阅读入口 + 组成稿件 + 范围与版本证据
    ↓ 真实完成内容、新发现与未决项回流研究部
下一次全局判断与研究目标
```

同一个题目可关联多个解法；同一个模式可有多个原题佐证。研究任务、问题身份、模式和阅读章是不同对象。改变章名或拆并章，不应强迫原题换ID或复制主讲解。研究部和两条工程线共用来源、记录、构建与传输；Agent承担对应职责，工具不自动决定下一章或下发目标。报告从记录生成，不反过来修改研究结论。

## 记录的责任

| 记录 | 它回答的问题 |
|---|---|
| 来源与入口 | 去哪里找、为什么找、实际查到什么、能否枚举 |
| 快照与清单 | 哪个版本、哪个范围、包含哪些外部身份，是否分页闭合 |
| 题目／案例 | 原题要求与条件、哪些部分读过、解法及处理去向 |
| 算法模式 | 为什么能这样做、适用条件、重要变种与替代方法 |
| 范围假说与内容关系 | 实际问题为什么共同成章、哪些拆分／关联、什么证据改变了划分；保存在任务README及已有研究笔记 |
| 当前研究目标 | 研究部为什么推荐这一范围、向哪条线交接、工程应继续研究什么、哪些未知项需反馈；同一任务README维护当前版本及变化依据 |
| 作者稿及代码 | 用户最后看到的讲解与实现是什么 |
| 任务笔记 | 哪些判断已经形成，尚不明确什么，如何继续 |

来源池采用 `schema_version: 1` 的版本化数据，`sources` 为来源记录集合；每个来源下的具体 `entries` 承担不同目录或正文入口。字段和状态值以实际数据格式与校验实现为准，本文不复制第二套枚举定义。

来源采用等级、访问观察、枚举能力、正文阅读与归类进度是不同维度。例如一个主力来源可以仅支持手动读取，一个可访问入口也可能尚未完整枚举。任何来源都不能因为网站标题中出现题数，直接获得该题数的完整处理状态。

外部稳定身份优先用于题目识别；显示标题和章节移动不应迫使身份改变。镜像、翻译及传播关系保存为关联，不能简单把十个转载 URL 视为十道独立题目。

## 确定性工具

命令统一入口为 `python -m second_algorithm`，实际子命令和参数通过 `--help` 查看。

| 能力 | 责任与边界 |
|---|---|
| sources | 查看来源与具体入口、用途和实际读取范围 |
| collect | 按声明范围取得与规范化清单；导入不会自动将条目标成已读 |
| validate | 核对身份、引用、摘要、记录与文件结构；不认证语义完备 |
| report | 生成来源池、处理进度和缺口视图；不成为另一份权威数据 |
| search | 用身份、别名、字段和文本定位实际记录与内容 |
| query-plan | 帮助组织待执行的检索方向；计划与真实执行结果分开 |
| propose-source | 登记待核来源，不自动提升为已采用或已读取 |

`search`只检索本仓库数据，不是全网搜索或语义检索；`query-plan`不执行查询，未登记的topic也不会自动建立计划。`collect`当前实际适配器只有`cses_html`、`codility_html`、`cpbook_table`和`link_index`，取得的是明确入口的目录元数据，不会下载并理解全部题干。自动正文研究、章节划分及正式发布命令当前均不存在；其他来源可由Agent实际读取后记录。

来源适配器按真实能力逐步增加；未适配来源可以通过实际手动阅读和结构化记录工作。CI 不应将任一外站的临时网络故障作为所有提交的阻塞条件，枚举器使用小型真实 fixture 作离线回归；联网观察另行记录。

## 两条线怎样使用同一工程

两条线开始前先读取研究部交接的目标版本。研究部使用现有来源、书目、清单、实际读件、模式、任务记录和真实发布入口梳理全貌，对影响选题的材料深入读取；目录扫描不提升为全文已读。实际发布状态以阅读入口及其范围／版本证据核对，不能从`authored`、构建摘要或Git提交数推断。

| 工作层 | 算法线的实际判断 | C++线的实际判断 | 共同落点 |
|---|---|---|---|
| 材料取得 | 原题目标、约束、题解／方法与分类差异 | 实现／修错任务、接口、语义与能力要求 | sources、inventories、私有原件及实际读件记录 |
| 形成章节 | 比较解法依据、判定结构、变种与组合依赖 | 比较代码任务、语言／库合同、版本与失败行为 | work中的候选关系、范围假说和划分依据 |
| 内容归并 | 同型问题、必要变种、主解和替代方法 | 共同机制、不同合同、贯穿实作及规则辨析 | cases／patterns与真实主讲解位置 |
| 实现核验 | 独立枚举、朴素或其他参考解法、区分性反例 | 类型／能力、生命周期、异常注入、版本、多TU或同步检查 | tests与实际验证摘要 |
| 单章交付 | 题型—思路—变种—代码的清楚组织 | 代码问题—机制—实现—变种的清楚组织 | content中的作者稿、源码和可用阅读入口 |

工作开始时用稳定研究任务ID保存材料，无需先给章命名。`work/<研究任务>/README.md`串联研究部的全局判断依据、候选与范围变化，形成当前有效的“研究目标”；工程在同一记录中承接目标版本、记录范围反馈和实际结果。目标说明对应线、具体问题群、为何现在做、纳入／暂不纳入、已有内容复用、材料与未知项及工程下一步，链接已有分析即可。局部实现细化直接进行，影响目标的范围变化由承担研究部职责的Agent更新版本与依据，再继续受影响部分；不要求新数据库、命令或审批。章名变化也不要求搬动全部资料。

现有目录继续使用：`catalog/`保存身份和来源事实；`work/`保存进行中的研究与依据；`content/<阅读单元>/`保存权威稿与派生版；`research/<日期>/`保存实际阶段结论和验证版本。某章由多份稿组成时，在阅读入口列明它们即可，不新增发布数据库。既有`work/**`冻结记录不因格式整理而重写。

构建调用为：

```sh
node tools/build_handbook.mjs <阅读单元目录> <稿名> [系列名]
```

例如现有算法稿可用`content/binary-search 二分查找`；C++候选稿可用`content/cpp 泛型与约束 求职C++实战总册`。参数指向实际文件，不代表预定章节。`package.json`现有快捷脚本仅`build:binary`，不能称已有`build:cpp`或自动逐章生产命令。构建需可用Node与项目依赖；机器专用运行时位置不写进公共命令。

代码以`// BEGIN id`／`// END id`对应作者稿占位引用，构建生成MD、HTML及摘要。修改源码／作者稿后重建受影响稿；修改共享构建器会影响全部构建摘要，需重建所有受影响输出。`tests/test_reading_assets.py`目前只发现`content/*/*.source.md`，因此沿用这一深度；将来确有必要加深目录时，必须同步检查发现规则，不能让新稿静默漏检。

结构与恢复用`python -m second_algorithm validate`和`python -m unittest discover -s tests -v`检查。实际C++测试根据问题风险选择；CI默认把`tests/cpp/*_test.cpp`按C++17编译，较新版本分支目前仅对已登记的测试额外实跑。新增C++20／23专用验证时须显式接入，旧模式skip不能算验证。多文件示例可参考`tools/verify_cpp_systems.py`的现有抽取与分编译办法，不要求所有新章都使用该特例脚本。

章节正式交付由Agent基于研究及核验作判断，在章入口明确状态和边界；已有模式状态、构建hash与Git传输均不是章节发布状态。候选稿可以同步仓库，不能因此在汇报中改称正式发布章。

## 冗余与版本

保留必要的两类信息：原取得结果使研究可回读，规范化记录使查询与核对可执行。摘要区分原字节与规范化结果；它们用途不同，不能互相冒充。

当前规范化清单保存在 `catalog/inventories/`，成功基线指针为 `catalog/inventory-heads.json`。原始页面缓存位于 Git 忽略的 `.local/materials/`，本机取得与失败记录分别位于 `.local/runs/`、`.local/failures/`。这些记录各有用途，不以本机缓存是否随 Git 存在判断远端清单是否有效。

最后成功清单与本次请求观察分开。失败不会把旧清单覆盖为空；新旧身份差异可追踪，历史记录不因页面暂时不再列出而删除。Git 历史和远端仓库保存版本，派生报告可重建，不增加并行权威数据库。

书籍和大体积读件留在本地 D 盘。公共仓库存可公开的元数据、定位、原创笔记和代码，不把用户原件、收费书籍、商业题库全文或本地缓存整包推送。

## 当前内容阶段

二分现已实际完成一轮来源发现、原题/教材阅读、归并、独立反查与内容修订，保留未补的进阶组合模式。权威作者稿为`content/binary-search/*.source.md`，同名`.cpp`为代码权威；`tools/build_handbook.mjs`装配可读MD与自包含HTML，`build/*.json`绑定输入/输出摘要。`tests/test_reading_assets.py`核对显示代码、文件链接和构建一致性；这仍不等于语义完备证明。

来源与研究清单仍保持区别：CSES目录取得400个任务链接，本轮案例记录实际读到其中5题；其他题不会因目录捕获而变为已读。二分当轮明确范围、读件、反查和真实下一步见[研究封存](../research/2026-10-26/binary-full-cycle.md)。

C++已有四种教材基座、七份候选稿和实际验证，见[阶段记录](../research/2026-10-26/cpp-full-cycle.md)。它们保留为预研资产，不代表七章已发布；其中已有作者内容与未充分研究分支分别存在。算法二分的三份稿也不是三章。继续时先研究候选问题关系，不能从这些文件名预定下一个章名。

当前纠偏和流程依据见[日志复盘](../research/2026-10-26/workflow-retrospective.md)；上游选题及目标交接职责以[研究部协议](../protocol/RESEARCH_DEPARTMENT.md)为准。下一步由`catalog/scope.json.current_frontier`及对应任务记录恢复；未有具体目标时先进行研究部工作，本次协议接入不冒称下一章目标已研究完成。所有能力以实际文件、命令输出与验证结果为准。新增运行平台、远程数据库或语义搜索应解决真实瓶颈；当前流程不依赖这些服务。
